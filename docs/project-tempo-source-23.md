# Project tempo source investigation 23

## Format evidence and boundary

The DAWproject maintainers' [XML reference](https://github.com/bitwig/dawproject/blob/main/Reference.html) defines `Transport/Tempo` as a `RealParameter` for setting or automating tempo. The [schema](https://github.com/bitwig/dawproject/blob/main/Project.xsd) allows `bpm` as a unit. The maintainers' [README example](https://github.com/bitwig/dawproject/blob/main/README.md) contains a Bitwig-authored `project.xml` whose `Transport/Tempo` has `unit="bpm"` and `value="149.000000"`. That example is an externally published format example, not a local Cubase fixture or a measurement of either current root.

`project-tempo-field-22.md` traces the installed DAWproject filter's source child virtual `+0x20` through a double-to-float conversion into the candidate host field. The successful parser-to-getter path is now linked below to `Transport/Tempo`'s `value` and RTTI-identified `DPProject`/`DPParameter` interfaces, but unit handling and error/default behavior are still unidentified. Accordingly, the format example does not establish that `MTempoTrackEvent+0x1b8` is BPM in every case, nor does it establish an actual value, active project, import, save or persistence. A local search of existing XML/JSON artifacts found no fixture with independently established tempo provenance.

## Import argument provenance

The fixed filter's import function starts at RVA `0x1f710`; it rejects a null `RDX` at `0x1f710–0x1f713` and copies the second Windows x64 argument into `R12` at `0x1f76b` (`4c 8b e2`). At the observed service call site, `0x1cb76` calls package-manager method `0x41b10`, wraps its result, and the wrapper's contained object is queried through virtual slot `+0x18` at `0x1cb9e`. The returned non-null pointer is moved to `RBX` and supplied as `RDX` to `0x1f710` at `0x1cbbe–0x1cbc8`. Thus the source receiver at `0x1f9e7` is the second argument of this import function, obtained from the package result's virtual `+0x18` in this specific service path. Package processing references `/project.xml` as documented in `dawproject-host-filter.md`; the further parser and child-getter link is described below, while unit behavior remains unestablished.

## Static parser-to-getter closure

In `dawproject.dll` RVA `0x4db70`, the parser selects a node using the ASCII key `Transport` at `0x1076f8` (`0x4de18–0x4de32`), then looks up `Tempo` at `0x100b70` (`0x4de5c–0x4de85`). For a non-null Tempo node it selects `value` at `0x107704` (`0x4ded7–0x4df15`), calls conversion helper `0x103a0` and loads the resulting double into `xmm6` at `0x4df3b`. This is the observed XML-key path; conversion failures, defaults and unit validation are not fully characterized.

The parser allocates an `0xe8`-byte object and calls constructor `0x43240` at `0x4e116`. That constructor installs primary vtable `0x105690`, secondary vtable `0x105708` at `+0x10`, and secondary vtable `0x105740` at `+0xb8`. Their MSVC RTTI type descriptors identify `Steinberg::DPParameter` with matching complete-object offsets. The parser calls the latter interface's slot `+0x58` at `0x4e16d–0x4e173` with `xmm6`. The slot target `0x435b0` is `movsd [rcx+8],xmm1; ret`, storing the double at complete object `+0xc0`. The same interface's slot `+0x20` target `0x3b4e0` is `movsd xmm0,[rcx+8]; ret`: it returns that stored double unchanged.

The parser's earlier object constructed by `0x43ed0` has secondary vtable `0x105da0` at `+0x10`, whose MSVC RTTI identifies `Steinberg::DPProject`. At `0x4e176–0x4e180`, helper `0x45be0` assigns the newly constructed object's pointer to that object's complete offset `+0x68`, retaining it through virtual `+0x08`. The `0x105da0` interface slot `+0x38` target `0x456f0` reads secondary `+0x58` (complete `+0x68`) and returns the assigned object plus `0xb8` when non-null. In the service path traced above, the project interface reaches import argument `r12`, and `0x1f9e7` slot `+0x38` followed by `0x1fa02` slot `+0x20` therefore reads this stored double. Combined with the previously documented `0x39200` call, the successful parsed-value route carries this double to the host float setter with single-precision conversion and no arithmetic scaling along the traced assignments and calls. The unit field's handling and malformed/missing-value behavior remain open; this is still static evidence, not a runtime BPM reading or persistence result.

Separately, `0x4e1b8–0x4e1c2` invokes stack-object constructor `0x46950` with `xmm6`; `0x46950` stores that double at its `+0xb8`. Its later use has not been established, and it is not the heap child returned by the project slot above.

## Independent package probe feasibility

The external DAWproject format is a ZIP container containing `project.xml`; the maintainer README's example supplies the shape of `Project/Application/Transport/Tempo` and a `bpm` unit. That format description does not prove a minimal package accepted by this fixed binary: required metadata, archive handling, parser errors and media traversal remain to be established before a controlled fixture is executed.

`CreatePackageManager` returns the manager secondary interface at complete-object `+0x10`; vtable RVA `0x105210` slots `+0`, `+8`, and `+0x10` target adjustor thunks `0x4288c`, `0x14628`, and `0x15188`, respectively, each subtracting `0x10` before forwarding. Slot `+0x18` points directly to `0x41b10`. In the observed service setup, the stack manager is constructed at `rbp+0x30` and `rcx=rbp+0x40` is supplied at `0x1cb76`: this is the **secondary interface**, not its complete-object pointer. This corrects earlier wording in `dawproject-host-filter.md`, which has now been updated. `RDX` carries UTF-16 path text; `R8` is a non-null client secondary interface. The manager query recognizes raw IID bytes `96 8b 2e 8d c3 68 1b 4c bd ca 97 e1 9c d2 38 99`, but those facts alone do not specify a full external ABI or initialization requirements.

On the observed successful construction branch, package constructor `0x41550` retains the project interface via its slot `+0x08`; the package destructor `0x415b0` releases it via `+0x10`. The service wraps the returned package interface and its `+0x18` getter reads a stored pointer (`0xf0a0`); whether that getter lends or transfers a reference must be established from the caller and implementation before building an external consumer. Manager slot `+0x10` forwards to release-like code, but the precise lifetime and error contract for all returned interfaces is not proven.

The client is not optional at entry: `0x41b49–0x41b4c` rejects null `R8`. The observed real client maps tags to host-derived Audio, Video, Preset and Midi destinations and manager invokes its virtual `+0x18` for each traversed media item. A later directory creation call exists in the path; complete extraction, traversal, normalization, collision and partial-failure behavior are unverified. A no-media XML design may avoid media-item iterations, but that is a hypothesis rather than proof of zero file effects. Process-global initialization, dependent modules, exception containment, and whether a standalone process can safely construct a client are likewise unresolved. Consequently no execution-ready ABI, complete write-scope guarantee, or justified one-shot package probe is asserted here. A discriminating static next step is to recover `0x41b10` failure/cleanup and every extraction write path, plus client string ownership and package/project getter reference semantics; only then can a uniquely isolated fixture and observed file-effects experiment be specified.
