## Required fail-closed gates before target-ready implementation

- Retain separately opened fixed process/thread handles; verify creation times, ownership, liveness, image path, x64 architecture and fixed disk PE. Verify actual loaded main-image base and its identity using clone-only reads after capture, without substituting target memory. Disk timestamp and preferred base are not file-version or loaded-image identity proofs. Check parent-directory reparse resolution and trusted installation tree; comparing a path string alone is insufficient.
- Observe global available physical and commit/pagefile capacity, target private bytes and total process/thread counts; define a conservative, explicitly approved threshold before capture and recheck immediately prior. Such metrics and thresholds do not constrain PSS allocation or copy-on-write costs. Preflight cannot guarantee a hard memory or latency bound, target scheduling, or that all threads remain unchanged. Toolhelp thread enumeration is non-atomic.
- `IsProcessInJob` reports membership, not the job's UI restrictions, breakaway policy, nested jobs, active-process limits or memory limits. The historical restricted-job audit is not a current verified handle or full policy. A target-ready implementation must obtain a justified read-only job-policy observation and prove which job applies; failure or uncertainty must stop. No implicit breakaway, force-breakaway or retry. [IsProcessInJob](https://learn.microsoft.com/en-us/windows/win32/api/jobapi2/nf-jobapi2-isprocessinjob), [PSS flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags).
- Review actual PSS handle rights, job restrictions, measured synthetic resource behavior and scheduling risk. Capture internally handles all target threads. No documented zero-freeze guarantee or fixed timeout is established; an outer watchdog cannot safely undo a synchronous capture and must not terminate the target or close the holder. `PssCaptureSnapshot` may itself fail before returning a snapshot. [PssCaptureSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot).

## Intended single-capture contract

After fresh successful preflight, one `PssCaptureSnapshot` with `PSS_CAPTURE_VA_CLONE | PSS_CAPTURE_THREADS | PSS_CAPTURE_THREAD_CONTEXT` and x64 control/integer context, timed by a monotonic clock; no retries, flag changes, or live-memory fallback. Capture time is an observation, not a scheduling-impact bound. Check the selected entry PID/TID/creation time, context size/flags and copy context while marker is valid. Query clone handle from this same snapshot. Private and shareable cloned mappings and context belong to one PSS result but a globally atomic cut and shared-section immutability are not documented.

Use serialized DbgHelp, clone-only `ReadProcessMemory` in strictly bounded region/read/byte/frame callbacks, including the symbol-handler `CBA_READ_MEMORY` path. Enumerate clone modules and compare to process module metadata without live memory reads; admit only actually verified direct System32 files or fixed Cubase installation files, resolve directory/file reparse points and reject all other paths. Validate loaded PE characteristics from clone against verified local files, and constrain explicit symbol/image paths to local verified files with no server, environment, UNC, URL or hidden network lookups; static flags alone do not prove total network isolation. Missing module/unwind data stops the walk. Never print raw stack, registers, pointer-shaped data or memory. Output module-relative PCs and classifications only, and distinguish initial frame echo from accepted unwind frames. Do not infer prompt causality or open completion.

For the first successful returned frame only, accept an exactly identical nonzero seed PC/RSP as an echo, not an unwind; thereafter require nonzero PC and strictly increasing RSP and stop on ambiguity, missing data, repetitions or budget exhaustion. Report incomplete/error separately from a complete, validated stack. Synthetic evidence does not establish real target correctness, symbol provenance, dynamic unwind behavior or safe read limits.

Release symbol state and marker, free local snapshot exactly once, and close all owned handles on all paths, recording each failure independently. Clone monitor wait timeout is not itself evidence of leakage. An independent supervisor can inspect clone PID/creation time after worker and handles exit, but a single absent inventory entry is not proof that all resources were destroyed. Record PSS status, timing, thread/clone metadata, classification and cleanup status without stack bytes. Preserve unknown prior host outcomes regardless of diagnostic result.

## Review and evidence limitations

The diagnostic enforces 8 GiB available physical / 8 GiB available pagefile / 2 GiB maximum target private bytes / 768 maximum target threads gates, with non-atomic observations and no allocation or time guarantee. It makes one PSS call without breakaway, uses clone-only explicit bounded memory reads, verifies clone main-image headers and eligible module PE metadata, limits frames, handles one initial echo and reports cleanup. The wrapper checks job policy immediately before starting it; that check is external and non-atomic with capture. Module identity validation compares PE metadata rather than complete content; path checks have time-of-check/time-of-use races, and process and file references may change. DbgHelp internal lookup/read behavior and strict local-only behavior are not established. The worker emits only partial walk results and is intended to exit nonzero even after a walk, avoiding a false completeness claim. The preflight does not bound CPU, transient suspension, or PSS commit. MSVC syntax/build passed and one live partial walk was observed; this is not a supported general-purpose target interface.

## Admission wrapper and callback accounting draft

`scripts/Build-ActivationClone23Target.ps1` writes an exclusive receipt after successful build, with the build ID, fixed executable path and SHA-256. `scripts/Invoke-ActivationClone23Target.ps1` accepts only a 32-hex build ID and derives the fixed filename, compares receipt path/ID/hash, then runs `ProjectOpenJobAudit20.Verify()` and requires the fixed target and holder, exactly one matching job and exact UI 64 / limit 8192. The hash is a narrow change-detection check for the reviewed diagnostic, not proof of source provenance; receipt and binary can be replaced together, and hash-to-execution has a race. The audit checks process creation times and liveness around its bounded holder-handle observation; it is not atomic with capture and does not exclude other nested jobs. A fixed exclusive admission reserves one attempt, including failed admission; interruptions may leave an empty reservation.

The wrapper creates a one-shot log directory, then uses `Start-Process -WindowStyle Hidden` with stdout/stderr file redirection. It records the worker PID and creation FILETIME and waits once for 60 seconds; timeout is reported without killing or retrying. The worker may remain running after wrapper exit. Whether redirection continues after wrapper exit in this environment has not been tested and must be validated independently before relying on the log as a complete record. Directory creation and executable verification have races and do not establish a protected filesystem boundary.

The target draft opens a temporary query-only clone monitor while its snapshot handle is retained, verifies the clone PID, records its creation FILETIME and closes the monitor before snapshot free. Failure is recorded and stops the walk. This identity permits only later independent inventory observation; process absence does not prove resource destruction. The draft does not modify target or clone Job membership.

The diagnostic stops emitting frames if its explicit bounded read or CBA_READ_MEMORY callback fails; a partial status is printed and no complete stack is claimed. Each emitted PC is a module RVA and is classified by clone mapping type; the reported `clone_disk_pe_headers` provenance means only that selected header metadata matched, not the identity of all mapped bytes or proof that DbgHelp used matching unwind information. The 2 MiB bound covers the diagnostic's explicit bounded-read callback calls, including its header checks; it is not a limit on every OS or DbgHelp internal read, allocation, memory footprint or I/O operation. Unsupported mappings and unknown modules stop output. Explicit local paths and DbgHelp flags reduce symbol search surface but have not been proven to enforce complete network isolation; file/path verification and later DbgHelp access have TOCTOU races.


## Lazy module loading revision

The coordinator reports a separate read-only target inventory with 172 modules; it is a point observation, not a verified capture-time set. The diagnostic registers a verified module with DbgHelp only when the current seed or most recently accepted frame PC is in that module, immediately before the next walk call. Each module is loaded at most once; a load or callback-read failure records the module name and partial stop, without retry or a search of alternate module paths. Module enumeration and clone/disk PE-header validation still occur up front for eligible modules, so this change reduces symbol-handler module loads rather than eliminating all per-module I/O. The observed target walk crossed modules before a later read failure; it does not establish universal correctness of lazy loading or DbgHelp's internal behavior.
