# Isolated desktop and process job boundary

The diagnostic launcher creates the owned target suspended on `winsta0\CubaseAI_MCP`. Before resuming its primary thread it creates an unnamed Windows job, sets `JOB_OBJECT_UILIMIT_DESKTOP` and `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`, assigns the process, verifies membership and queries both flags. A failure stops the newly created process and reports an error; there is no unrestricted retry. `CREATE_BREAKAWAY_FROM_JOB` is used so a holder already inside a job can create this separate UI-restricted job when the parent job permits breakaway. If the parent job disallows that operation, creation or assignment reports the Windows error. The holder retains the job handle until the target exits; closing the last job handle terminates remaining job members. Microsoft documents the [desktop UI restriction](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions) and [nested-job constraints](https://learn.microsoft.com/en-us/windows/win32/procthread/nested-jobs).

The launcher reads the input desktop before creation, immediately before resume and immediately afterward, and rejects the target desktop if it is the current input desktop. Its receipt records these samples, the foreground handles and the verified job flags. These are point observations, not continuous foreground monitoring. The job restriction applies to members and to the documented `CreateDesktop` and `SwitchDesktop` functions; it is not a claim that outside processes, every child-creation mechanism, all GUI behavior, or every possible foreground event is controlled. Private dialogs may still block the application, and the job is not a MIDI handshake or project lifecycle interface.

`tests/desktop-job-boundary.ps1` compiled and launched a synthetic process on a different private desktop. The child reported job membership, UI flag `0x40`, and `CreateDesktopW` failure with error 5; sampled input desktop was `Default` and foreground handles matched. Evidence is under `artifacts/desktop-job-09f0a77448e04f9984f5e5e075c5e468/`. No desktop-switch call was made by that test. In the separate user-approved isolated Cubase restart, PID 50568 received the same verified job flags and the three input-desktop samples were `Default`; project and score windows later appeared on the private desktop. This is a real start observation, not a completed project operation or proof that foreground events never occurred.

The `-Background` path now starts its hidden holder with `CreateProcessW` and `bInheritHandles=false`. The holder writes its startup receipt and caught script errors to separate pre-created runtime log files itself, so it does not keep the caller's captured output pipe open. These logs cover the script's explicit receipt and caught errors, not every native crash or early runtime failure. `tests/detached-holder-pipe.ps1` verifies that a synthetic long-lived holder remains alive while its starter and captured pipes close; `tests/background-launch-pipe.ps1` separately verifies the existing-Cubase guard without replacing the live instance. The new detached-holder path has not yet been used for a fresh Cubase launch; the real PID 50568 launch used the earlier holder-spawn path after the new job restriction was added.
