This method checks informer `+0x90` is nonzero and the incoming object is non-null, then passes that object and literal `Idle` to `0x3a8cdc0`; the result must be nonzero. It also requires a different global object to be non-null, its `+0x37` byte zero, its secondary interface slot `+0x60` return zero, and its `+0x34` byte equal that zero result. Only then does it invoke `0x25b0a40`. If informer `+0x54` is positive it decrements it and invokes that function; otherwise it calls `0x3675a80`, sets informer `+0x50` to zero and invokes the same function. The meaning of these fields and the object's event registration, dispatch thread and timing remain unverified; literal `Idle` is a comparison input, not proof that a particular observed process received an idle notification.

`0x25b0a40` creates a temporary ordered tree and reads a global pointer at executable RVA `0x5512810`. If that pointer is null, it exits the main enumeration path. Otherwise, it calls the source object's secondary interface at `+0x10`, virtual slot `+0x18`, to obtain a signed count, and iterates indexes through `0x29af2b0`. For each non-null returned object, virtual slot `+0xd8` must succeed on a temporary wrapper; its secondary interface `+0x10` must then return nonzero from slot `+0x20` for literal `midi` and slot `+0x28` for literal `system`. Qualifying wrapper values participate in ordered-tree comparison at node `+0x20` using `0x3b7f430`. After comparing old and newly collected trees, `0x25b153e–0x25b1590` clears informer `+0x58`, copies the newly built tree and stores its count at `+0x60`. It is therefore a refresh/replacement path, not simply an isolated insert. Observer notifications and exact node value types require further tracing.

## Registry source follow-up

The initialized pointer stored at executable RVA `0x5512810` points to the static object at RVA `0x5928a80`. Initializer `0x14b9700` passes that object to constructor `0x29e1e00`, which installs primary vtable `0x44d8308` and secondary vtable `0x44d83d8`; their MSVC RTTI names `PPortRegistry`. The constructor initializes a `CmArray` subobject at registry `+0x20` with vtable `0x4825ab8`. Registry secondary slot `+0x18` reaches the array's slot `+0xd0`, whose leaf `0x15eb9a0` reads array `+0x1c`; `0x29af2b0` reaches array slot `+0x108`, whose leaf `0x1653970` checks that count and then indexes the pointer array at `+0x20`. Thus the concrete registry count is object `+0x3c` and its array pointer is object `+0x40`, subject to exact runtime-vtable validation.

The expanded diagnostic verified that exact source pointer and all three vtables, bounded the array to 256 observed entries, and reread its header and elements. In PID 3720 at `17:16:58Z`, the registry had count 19, capacity 20 and stable headers. Four entries with exact `PMmeMidiInSocket` or `PMmeMidiOutSocket` vtables had the two expected MCP port names in both socket classes. The helper decoded only the statically verified `PPort+0x50` `FString` fields for those two exact vtables, with bounded lengths and repeated bytes; it did not invoke a virtual method. Evidence is `artifacts/ipc/midi-port-registry-names-3720.json`; offline RTTI mapping for the five observed vtables is `artifacts/research/session-09/port-registry-rtti.json`. This shows that the named sockets were present in the registry at that instant, not that the informer filter accepted them or that callbacks or detection ran. The two sampled informer tree counts were zero in that snapshot; host-environment collections were observed empty in a distinct earlier snapshot.
