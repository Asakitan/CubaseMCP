One later-traced `MProject` sender supplies the incoming root object's `+0x98` subobject; see `docs/midi-project-notifications.md` for its conditions and live-evidence limits.

## Downstream state and snapshot limits

`0x25afa20` enumerates the registry at executable `+0x5512810`, filters objects using `midi` and `system` virtual checks, obtains their identifier wrappers, and builds a temporary ordered set. For resolved entries it notifies informer observers at slot `+0x08`; it also compares identifiers against the separate tree at complete `+0x68`, performs associated cleanup, then clears the port tree at complete `+0x58` and sets its count `+0x60` to zero. This is a static invalidation/notification path, not proof it was executed in the current process or that a later refresh succeeds. Its exact cleanup semantics remain under investigation.

The Idle method `0x25af940` tests the project-tree count `+0x90` for nonzero along with other conditions before calling the port refresh `0x25b0a40`. Existing evidence `artifacts/ipc/midi-port-informer-gates-3720.json` observed this count as zero with stable double-read headers. It establishes only the gate input at that instant; it does not prove a project was absent, the callback was never delivered, or why the key set was empty. Reading an empty tree yields no pointee to identify; no new process read was necessary for this slice.
