# Binding experiment port host 26

`scripts/Start-BindingTestPorts26.ps1` is a separate diagnostic holder for the exact loopback names `CubaseAI Binding26 To Cubase` and `CubaseAI Binding26 From Cubase`. It uses the installed virtualMIDI library and the same `MidiPortHost` class as the production port host; it neither changes the production port configuration nor starts Cubase. Its fixed names and owner mutex are separate from the production ports and mutex. It is not a second MCP backend.

For a fresh 32-hex run ID, the hidden `-Background` coordinator first requires no observed Cubase process, creates unique log paths and starts a worker without inherited capture handles. `starting` reports only the worker PID. The worker derives the ID from its paired fixed log filenames, repeats the no-Cubase check, rejects observed name collisions, creates the two ports, checks that each name is unique in both input and output enumerations, and atomically publishes a run-specific `ready` receipt with its PID and process creation FILETIME. After six minutes a periodic cleanup request closes the ports only when no Cubase process is observed; it remains deferred while Cubase is running. `-Stop -RunId RUNID` checks no Cubase is observed, the receipt, executable and process lifetime immediately before signaling the run-specific request. The worker checks again before closing. It does not terminate Cubase or the production MIDI host.

Name enumeration, process checks and receipt creation are sequential; they do not protect against a concurrent third-party Cubase start. The deadline and stop request do not establish that any controller mapped the ports or that a Cubase request completed. A failed start or missing receipt is not a reason to replay a later host operation. The no-Cubase lifecycle guard was added after the observations below; a new guarded lifecycle must be verified before reliance for an A/B experiment.

An initial version used `Start-Process` under a captured PowerShell caller. Run `a0c1082f4aa5f6fde82241b4dbe0a7e0` produced a worker-ready receipt, but the coordinator's capture did not return until the worker was stopped; the smoke failed without starting an A/B controller or issuing a host write. A separately invoked exact-run stop signaled the worker once. The holder was changed to the existing no-inherited-handles launcher, with explicit file logging, and exercised in the distinct run below.

The corrected detached-holder smoke `artifacts/ipc/binding26-ports-smoke-f153fadfe2298de2065ccdd9e9f6a44d.json` returned in 0.885 seconds, observed both ports, and stopped them while PID 72128 was still running. The worker and production process identities remained the same, but a subsequent single MCP status request timed out with `execution: unknown` (`artifacts/ipc/binding26-post-port-status-aaf9c012-99aa-4b34-a975-4cbec97e1e92.json`), and the controller console later recorded `device deactivated` (`artifacts/ipc/post-binding26-ports-Read-MidiScriptErrors-343af2a5b7f0490c8895e4b332b1f291.json`). A later console sample contained no new activation and the host model still contained the temporary names (`artifacts/ipc/post-binding26-settled-Read-MidiScriptErrors-6ab0d45c0cb64289bce2cc2d08ea977f.json`, `artifacts/ipc/post-binding26-settled-Read-MidiHostEnvironment-9336e07856814253870a7e2fc52401d2.json`). The OS still listed one exact production input and output, and the port host listed PID 72128 as a client (`artifacts/ipc/binding26-doctor-ports-7fcffe418d1c4b44b6255da4c56846f2.json`, `artifacts/ipc/binding26-production-port-clients-d7dd2330249c4aada2db024afd63ffb4.json`). These snapshots do not prove operational mapping or exact internal cause. The timed-out status request was not repeated.

The current guard prevents starting or stopping diagnostic ports while Cubase is observed; the existing-instance rejection passed (`artifacts/ipc/binding26-ports-guard-8c7393af620387ea33f5ad0b64b0623e.json`). Its check and another process's creation are still non-atomic. A future orchestrator must create diagnostic ports before the owned Cubase process and stop them after it exits. The timer defers cleanup while any Cubase is observed; driver failure or concurrent third-party starts remain outside that guarantee.

One fixed `WM_DEVICECHANGE/DBT_DEVNODES_CHANGED` notification was subsequently delivered to the owned USB listener (`artifacts/ipc/device-refresh26-result-72128.json`). A console sample six seconds later still ended with device deactivation and no newer activation (`artifacts/ipc/device-refresh26-script-c97af1d8605a43dea079fe23033b5185.json`); delivery is not a reload or reconnection guarantee. A separately prearmed observer recorded 259 samples over approximately 60 seconds with input desktop `Default` and the same foreground handle and PID (`artifacts/ipc/first-project-open24-observer-72128-669ab6bf4f37733b4f1e17f3ac371a85.json`). Polling and caller-desktop limitations apply. The notification and the timed-out status request were not replayed, and mapping restoration remains unverified.
