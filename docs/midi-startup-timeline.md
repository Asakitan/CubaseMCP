# MIDI startup read-only timeline

`scripts/Trace-MidiStartup.ps1` samples the fixed Cubase 16.0.5 x64 project and informer globals, project root and listener chain, and informer project-tree header. It makes no target calls or writes and does not change UI, processes, ports, or settings.

Run `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Trace-MidiStartup.ps1 -TargetProcessId PID -DurationSeconds 30 -IntervalMs 100`. Duration is 1–300 seconds and interval 50–5000 ms; the longer bound accommodates a measured startup that remained in initialization for more than 30 seconds. Output is a uniquely named `artifacts/ipc/midi-startup-timeline-PID-RUNID.json` and stdout; existing evidence is not overwritten. An error status returns exit code 1. Pending is distinct from a measured negative.

For a deliberately controlled restart of an owned isolated test project, the `-NextLaunchRunId RUNID -PreviousProcessId PID -NextProjectPath PATH` parameter set compiles the reader before the next process starts. `RUNID` is a fresh 32-character lowercase hexadecimal identifier. The previous receipt's project must be an owned file under `artifacts/live-smoke`; the explicit next path must be an existing, non-reparse CPR in the same directory, whether it is the same file or a distinct fixture. After verifying the preceding launch and both project paths, the reader creates `artifacts/ipc/midi-startup-arm-RUNID.json` with `status=ready` and waits up to 90 seconds. The launcher coordinator then creates a new `artifacts/ipc/midi-startup-ticket-RUNID.json` containing `runId`, `previousPid`, the new launcher `hostPid`, and the exact next `project` path. The reader accepts only a matching launch receipt for the private desktop and explicit next project, with a new PID and a process start after arming, then records `midi-startup-timeline-next-RUNID.json`. The coordinator, not this reader, controls the process lifecycle. The ticket should be created atomically after the launcher returns its host PID. Arming earlier than process creation reduces compilation latency but does not make sampling atomic or guarantee observing the first transition.

Session 24 adds a separate `-EmptyLaunchRunId RUNID -PreviousProcessId PID -PreviousCreationFiletime FILETIME` prearmed mode for a launch with no CPR command-line argument. It verifies the prior owned project or a prior empty receipt and exact process lifetime, atomically publishes `midi-startup-empty-arm-RUNID.json`, and waits for a matching `midi-startup-empty-ticket-RUNID.json` containing the run ID, prior PID and creation FILETIME, new holder PID and creation FILETIME, `mode: empty`, and an explicit `project: null`. It then requires the distinct `cubase-empty-launch-24-RUNID.json` receipt, matching run ID, PID, holder PID, creation FILETIMEs, private desktop and Boolean restricted Job flags. In the current source, a stable sample with a project object, informer, its listener and an absent root is labeled `root_absent_observed`; this label alone does not prove the informer tree or every project is empty. Uninitialized or incomplete fields remain `pending`. The initial session 24 live trace used the earlier label `observed_empty`; its source snapshot is preserved with its backup. The current source also flushes each empty-mode sample to `midi-startup-timeline-empty-RUNID.jsonl` before writing the final JSON summary; a terminated write can still leave a partial final line. The sampler never stops or launches a process. A null command-line project is not proof that Cubase has no automatically restored project, no Hub, or a completed project operation; the sampled root and window states must be observed separately.

The explicit `-TargetProcessId PID -TransitionRunId RUNID` mode streams samples to `midi-project-transition-PID-RUNID.jsonl` and publishes a CreateNew/rename ready receipt only after a stable root-absent, empty-tree, listener-present sample on an observed private desktop with a different input desktop and foreground PID. The receipt identifies the sampler and target by PID and creation FILETIME; an outside coordinator must verify the sampler remains alive. It does not launch the host or perform project operations. The final JSON remains the regular uniquely named target timeline; a ready sample is non-atomic and does not guarantee later state.

The reader verifies launch PID/desktop and metadata timestamp against process start, executable path, version, PE machine/timestamp and image base; prearmed mode also requires the new receipt's job flags. At each sample it checks process identity, records the input desktop and caller-desktop foreground handle/PID, counts target-owned private windows and records their visible titles, then checks project/informer globals and the established project, root, listener container, and informer vtables. A sampled target input desktop or target foreground PID sets `backgroundViolation`; these sequential polling observations may miss transient events and the foreground call is not a complete cross-desktop history. It records project, root, listener and informer fields independently: for example, an absent root does not suppress a valid listener or tree observation, and an absent informer does not suppress a valid project/root observation. An uninitialized global or no observed owned private-desktop window is pending, not a negative ownership or registration result; a stable zero root is reported as `rootState=absent` for that sample. Desktop enumeration failure is an error. The listener chain is bounded to 128 nodes, cycle checked, length checked and double-read, along with globals, relevant object fields and root. The tree count is bounded to 4096; when a validated root exists, a separately bounded 64-node search checks whether its `+0x98` pointer is a tree key. Sentinel and traversed nodes are reread; a null result means the root or informer was not ready, not a negative match. Read failures, invalid layouts, and changed snapshots are errors, not zero values. Each sample is timestamped and reports observed, pending, or error. A missing process or changed PID start time stops the capture as a terminal error.

Polling can miss transitions; stable rereads are not an atomic snapshot and do not establish callback event history, ownership or causal order. In the direct PID mode, compilation and preflight happen after the supplied process starts; even in prearmed mode the launch receipt and validation occur before the first sample. Compare the first sample timestamp to process start. Private-desktop absence early in startup leaves process desktop ownership unverified for that sample even when other fields were readable. Captures contain runtime addresses and should be treated as local diagnostics. Use fresh launch metadata for each process; recorded addresses from older runs are not reusable.

## Session 10 observations

PID 3720 had a root and registered informer listener, but the informer project tree was empty and did not contain that root (`artifacts/ipc/midi-startup-timeline-3720-552e48f89323406d86396472e2bf2043.json`). This capture began long after process start and is not startup chronology.

A first approved restart retained a prior `ApplicationStarted.txt` marker. Its PID 40204 had the cached marker decision and initialized bytes both set, and a Safe Start window was observed. The first launch-ticket coordinator accidentally waited on a pipe inherited by the long-running desktop holder; the ticket was delivered after a delay. Consequently, `artifacts/ipc/midi-startup-timeline-next-e6ffb0dbb46d41fa8f5b5a099f784b67.json` begins 34.85 seconds after that process started. Its sampled root and informer were absent, but the omitted interval and startup branch prevent a complete ordering conclusion. The marker/cache evidence is in `artifacts/ipc/startup-flags-40204-session10.json`.

A corrected controlled restart backed up the owned project and prior receipt, archived the known transient marker while Cubase was stopped, and started PID 53000 on the same private desktop. The holder process was launched directly with its output redirected to files so its PID could be ticketed immediately without waiting for its lifetime. The foreground handles in the receipt matched; a project window subsequently appeared. Archiving a known startup marker is not a project operation or a substitute for a live MIDI handshake.

The prearmed capture `artifacts/ipc/midi-startup-timeline-next-9eb33f175e2945eb8287dd8581724d42.json` began 94 ms after process start. The first readable root appeared at `17:36:25.571 UTC`; in 11 successive samples up to the first readable informer at `17:36:27.164 UTC`, the root pointer stayed the same and the informer global was zero. The first observed informer was in the listener chain, with an empty project tree. All 566 readable informer samples, including that first observation, through `17:37:49.523 UTC` showed an empty tree and no current-root key. One earlier sample at `17:36:19.730 UTC` had a private-desktop enumeration error, so the capture's aggregate status is `error`; there were no sample errors in the stated root-to-informer interval. Polling can miss intermediate changes, and these observations do not prove the identity of a dispatched callback, that no notification was ever received, or the reason for the empty tree.

PID 53000's script console contained the revision 3.3 construction message without an activation message. A separate no-write MCP status request timed out with outcome `unknown` (`artifacts/live-smoke/verification-coverage-3.3-53000.json`). The 23-tool listing and project window are not proof of a live control path.
