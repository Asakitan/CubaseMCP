PID 24036 / process creation FILETIME 134387250823263004 and TID 59956 / thread creation FILETIME 134387250823263010 are historical identifiers for the separate investigation, not a fresh identity verification. Both previously submitted opens remain unknown and must not be replayed.

The combined flags `PSS_CAPTURE_VA_CLONE | PSS_CAPTURE_THREADS | PSS_CAPTURE_THREAD_CONTEXT` (`0x181`) provide a promising single-snapshot source for thread context and cloneable pages; they do not establish a documented globally atomic register/page cut, nor that every relevant page or dynamic unwind table is available. Microsoft describes all MEM_PRIVATE regions and shareable MEM_MAPPED / MEM_IMAGE sections as cloneable, and all thread contexts as captured. Shareable mapped contents may be changed by other processes; do not assume immutable point-in-time bytes for every mapping. Inspect actual region and access success; never substitute a later live-process read. [Capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags), [capture](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot).

## Material risks and release gates

- PSS documentation examined does not specify zero scheduling impact, a no-suspension guarantee, or an upper capture latency; capture may affect every target thread. It also does not quantify peak committed memory or copy-on-write pressure for this workload. A small output or bounded walk does not bound capture resource cost. Require an explicitly approved resource and latency budget, a prior independent synthetic-process experiment, and a stop/cleanup plan before any target operation.
- A VA clone creates a process, unlike the previous context-only capture. The known target job has UI and lifetime restrictions; clone job assignment, job resource/active-process limits and side effects on this exact system are not established. No breakaway flags should be silently chosen: optional breakaway can still create the clone inside the job, breakaway follows job policy, and force breakaway requires TCB privilege. A failure is a stop, not justification for another flag or fallback. [Capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags).
- The known private desktop and holder job are part of the running environment. Do not open, switch, enumerate or operate the desktop for this experiment; do not close the holder handle. Microsoft pages reviewed do not establish the clone's desktop/job interactions or whether all relevant inherited resources have no side effects. Treat these as unresolved, not evidence of no impact.
- Required exact process rights for this flag combination and any policy/privilege constraints are not specified by the cited capture page. PROCESS_CREATE_PROCESS is a documented right to create a process, not a documented complete PSS access mask. Determine rights with authoritative evidence and a synthetic child test; request only reviewed rights, report access denied and stop. Elevation does not establish success or absence of impact.

## Proposed target bounded walk, not implemented

1. Keep process and thread handles open; check PID, TID ownership, creation times, liveness, machine, expected image identity. Identity checks before and after are sequential and do not prove no state changes in between. Make exactly one reviewed capture with the three flags and required x64 context flags; no automatic retry.
2. Walk the snapshot thread entries, match all identifiers and creation time, check `SizeOfContextRecord` and context flags and copy the context before the marker is released. Query `PSS_QUERY_VA_CLONE_INFORMATION` for `VaCloneHandle` while the snapshot remains alive. The documentation describes the handle but does not state independent ownership; do not independently close it absent authoritative ownership guidance. [Thread entry](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_thread_entry), [clone information](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_va_clone_information).
3. A single-threaded DbgHelp session should use an explicit local-only symbol path, with no inherited `_NT_SYMBOL_PATH`, URL, `srv*`, UNC path, or implicit network source. `SymInitialize` with non-null explicit local path and `fInvadeProcess=FALSE` avoids the default environment path and implicit module enumeration; separately load only verified clone-address image mappings and matching image identities. Prevent symbol and image lookup outside the approved local allowlist, including DbgHelp image lookup and reparse points; a local-looking path alone is not a complete network prohibition. Missing verified mappings/unwind information is a truncation, not a reason to use the live target or blindly trust a same-named disk image. [SymInitialize](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-syminitialize).
4. Feed a copy of the snapshot context to `StackWalk64` with AMD64 PC, stack and frame initialized, and use a clone-only memory callback shared with the documented `CBA_READ_MEMORY` symbol-handler callback. Every read must enforce region, total-byte, individual-read and frame-count bounds, overflow checks and full-read success; reject unreadable or unsupported mappings. Supply matching function-table and module-base callbacks. Keep DbgHelp calls serialized; stop on missing data, no progress, invalid stack progression or budget exhaustion. `StackWalk64` may modify context and generally does not set last error on failure; distinguish normal termination from proven failure only where separately evidenced. [StackWalk64](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-stackwalk64).
5. Report only initial context and bounded module-relative frames with each mapping/unwind source, stop reason, and whether relevant bytes were private or shareable. Do not print, save, or transmit raw stack words. An actual successful unwind based on snapshot context and validated unwind information is stronger evidence than scanning pointer-shaped words, but it remains conditional on capture consistency, metadata, dynamic code, and DbgHelp correctness. It does not prove which prompt is active, its decision, or completion of either open.
6. On every path release symbol state (`SymCleanup`), marker, then the locally held snapshot using `PssFreeSnapshot(GetCurrentProcess(), snapshot)` once, and close separately owned process/thread handles; record cleanup errors separately. Snapshot lifetime and any clone process/resource release following PSS cleanup must be verified using an independent synthetic child, not assumed from a successful return. The API explicitly warns against concurrent or repeated free. [PssFreeSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssfreesnapshot).

## Synthetic-only source prepared

`native/ActivationClone22.cpp` and `scripts/Build-ActivationClone22.ps1` contain a synthetic-only experiment. The parent starts its own child, synchronizes with two inherited events, captures the child main thread and VA clone, attempts a bounded DbgHelp unwind, and reports whether three named noinline functions appear with increasing stack pointer. It accepts no PID and has no Cubase mode. The child has a timeout, so failure does not require operating a target window.

The top-level review restricted inherited handles to the two events, required clone module enumeration and comparison by base, size and path with the waiting child, rejected reparse-point image and PDB files, checked the requested symbol options, enforced expected frame order and monotonic stack progression, and added a clone-exit observation after freeing the snapshot. ## Static review of first synthetic failure

The old loop combines three distinct outcomes (`pc == 0`, `rsp == previous`, `rsp < previous`) into `rsp_progress=0`; its first comparison is against the supplied captured RSP, before any earlier returned frame has been accepted. Thus the first result did not establish which condition occurred, or that any returned pair of successive walked frames failed to progress. The contract requires initialized addresses and says the context can be modified; it does not promise strict RSP increase on the first call. A later synthetic run below identified an initial echo in that run. [StackWalk64](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-stackwalk64), [STACKFRAME64](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/ns-dbghelp-stackframe64).

The snapshot-free result establishes successful return of `PssFreeSnapshot`, not the meaning or completion timing of the clone's process-exit transition. The earlier monitor waited before releasing the synthetic child; the measured timeout therefore does not distinguish a clone lifetime coupled to that child from other reasons. Microsoft describes freeing the snapshot but does not document a two-second clone termination deadline or state that monitoring-handle waiting is a resource-release criterion. [PssFreeSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssfreesnapshot).

An intermediate synthetic-only revision added a first-failure frame index, zero/same-PC booleans and the RSP relation only, never raw stack or pointer values. It retained the monitor until after the synthetic child exited and printed a second wait outcome; at that point the original pre-child wait remained a required success condition. That revision was built and run once as described below.

## Synthetic run 23: observed initial frame and clone lifetime analysis

The top-level agent reports one synthetic run `409c8adae69b4112b185a0de8b42919d`: `walk_stop index=0 pc_zero=0 pc_same=1 sp_relation=equal`, snapshot free returned 0, and both the pre-child and post-child clone-monitor waits returned `WAIT_TIMEOUT` (258); exit status was 1. This establishes the first successful StackWalk64 result repeated the seeded PC and RSP in that run. It does not establish how later frames would behave, because the loop stopped immediately. It also does not establish a general DbgHelp contract requiring the first result to repeat the seed.

Microsoft documents that `PssFreeSnapshot` frees a snapshot, and separately that a process wait becomes signaled upon termination; it does not document a bounded clone process-signaling time, or whether the queried clone process is threadless. A separate open monitor handle adds an object reference and retains a handle until closed; holding a process handle after termination retains the process object, but ordinary process handles do not prevent termination signaling. `WAIT_TIMEOUT` establishes only that the object was not signaled during each wait. It does not establish that code was executing, that a supposedly threadless clone has live threads, that PSS cleanup failed, or that the snapshot resources were all released. Likewise, `PssFreeSnapshot == ERROR_SUCCESS` alone does not prove every retained clone-related object has been destroyed. The behavior of an initially threadless PSS VA clone is not established by the ordinary rule that a process terminates when its last thread terminates; no thread inventory was captured in this run, so calling this clone definitively threadless would exceed the evidence. [PSS free](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-pssfreesnapshot), [process termination](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process), [object references](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/life-cycle-of-an-object), [process wait state](https://learn.microsoft.com/en-us/windows/win32/procthread/synchronizing-execution-of-multiple-threads).

For a future independent synthetic lifecycle experiment, separate an outer supervisor from an inner snapshot worker and its synthetic target child. The worker records clone PID and creation time, capture/free results and successful closure of every separately owned clone monitor, then exits; the supervisor waits for the worker to exit before performing bounded process-inventory observations without holding a clone handle. Compare PID **and creation time** on any subsequently opened query handle, close each query immediately, and report access denied, PID reuse and enumeration limitations as indeterminate. A later absence from an inventory is an observation about that enumeration, not proof of destruction of all objects or memory; a query handle itself can transiently retain an object and cannot observe its deletion while retained. A separate controlled baseline with no monitor could test whether monitoring changes the observation, without claiming that either outcome is a universal Windows contract. This is an experimental design, not a performed test, and it should avoid repeated unbounded polling or any target process.

### Bounded unwind initialization rationale

Seed the frame from the copied context and retain the initial PC/RSP pair. For the first successful `StackWalk64` result only, permit exactly one identical, nonzero PC/RSP pair as an initial-frame echo; consume it without counting it as a newly unwound frame. If the first result differs, apply the ordinary checks immediately. On every subsequent successful result require nonzero PC and strictly increasing RSP relative to the last accepted pair; terminate on equal or decreasing RSP, repeated pair, failed bounded reads, missing required metadata, ordering error, or frame/byte limit. Keep the synthetic named-function ordering check and report whether an echo was consumed, actual accepted frame count and termination category. An echo is not independently evidence of an unwind; a passing synthetic trace requires the three functions in order plus required metadata and cleanup observations. This exception is justified only as an accommodation for the observed run, not a documented universal convention.

## Synthetic diagnostic revision prepared after run 23

The synthetic-only C++ draft now consumes an initial successful StackWalk64 result as an echo only when both nonzero PC and RSP exactly equal the seed; this can occur only at index zero. Every later accepted frame must have nonzero PC and strictly higher RSP, with the existing ordering, bounded reads and frame limit. Output includes echo and accepted-frame counts, not raw stack values. While the snapshot-provided clone handle is held, the monitor is checked for the same PID and its creation FILETIME and close result are recorded. Wait timeouts are recorded but no longer treated as proof of resource leakage or a failure by themselves; WAIT_FAILED remains failure. Snapshot free failure remains failure.

`scripts/Build-ActivationClone22.ps1` creates a distinct `run-RUNID` directory for each 32-hex build ID rather than overwriting existing evidence. `scripts/Observe-ActivationClone23.ps1` is a synthetic-only supervisor for one existing build selected by its build-run ID. It starts exactly one `synthetic-parent`, waits up to 60 seconds without killing it, and after worker exit and reported monitor closure performs one process inventory and compares the clone PID and creation time. It labels the result matching identity, absent from that inventory, reused, access denied or unverified. This is a bounded observation rather than proof of kernel-object destruction or memory reclamation; the act of obtaining and querying a candidate may itself hold a temporary handle, and inventory visibility, process exit races and access checks limit interpretation. A worker timeout reports its PID and creation time for follow-up, leaves lifecycle unverified and does not initiate a retry. The supervisor reports the worker exit code separately and exits nonzero for any outcome except observed absence paired with a zero worker exit; an observation is not a replacement for a successful unwind or cleanup status.

The public [sysinfo Windows source](https://docs.rs/sysinfo/latest/x86_64-pc-windows-msvc/src/sysinfo/windows/system.rs.html) is an implementation lead, not a Microsoft API guarantee of PSS clone thread count, signaling, or lifecycle.

## Restricted synthetic job mode draft

`synthetic-job-parent` is a separate fixed mode of the synthetic executable and accepts no PID. It creates its own unnamed Job, sets and queries UI limit `0x40` and limit flag `0x2000`, creates its own synthetic child suspended, assigns it to that Job, verifies membership, then resumes the child before the existing one-shot PSS/unwind sequence. Setup failure stops before capture; cleanup resumes a still-suspended synthetic child, and if it remains suspended or resume fails, attempts to terminate only that owned child. It then releases the event, waits, and closes the Job, with each Job step and close reported. Closing a kill-on-close Job can terminate remaining members, including any clone assigned to it; a later absent clone observation is therefore not proof that PSS free alone destroyed it. Existing outer Job constraints, nested-job rules and UI restrictions can reject setup. PSS clone membership in this Job is not assumed; it requires separate observation.

The supervisor accepts only `synthetic-parent` and `synthetic-job-parent`, reports the mode, and for the job mode requires reported successful Job-handle closure before its single post-worker inventory observation. The mode was subsequently built and run once, as recorded below. It mirrors two numeric flags only, not the full target Job tree, concurrent application state, workload or clone-resource consequences, and it does not establish that a target capture is impact-free.
