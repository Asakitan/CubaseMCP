# Candidate second-instance routing: static evidence and test gate

Read-only analysis of the locally installed Cubase AI 16.0.5 x64 executable (PE timestamp `0x6adf121b`). No second instance, process modification, UI action, license change, project operation or synthetic window message was performed. Reproduce the selected disassembly and imports with `E:\Py\python.exe scripts/project-instance-routing-inspect.py`; the inspector validates machine, timestamp and image base and decodes from PE runtime-function starts before filtering output. This identifies internal behavior, not a supported IPC contract.

## Candidate sender and receiver

A decoded direct call at `0x3935a49` invokes `0x3940920`; its overall entry conditions and execution during a real launch are not yet established. The latter routine bypasses its lookup if incoming `cl == 3`; otherwise it calls `FindWindowW` with a class-name value stored in process state and a null title. For a found window it has further state checks and sends `0x42c` synchronously via `0x3944020`; only a response `0x2871c93` follows the branch discussed below. This is a candidate running-instance discovery/handshake, not proof that every launch uses it, that the correct host window is found, or that the path works across Windows desktops.

After that handshake, `0x394098f` calls wrapper `0x3944120` on the found window. On its normal branch the wrapper calls `USER32!SetForegroundWindow`; another state-dependent branch returns before that call. **This explicit foreground operation conflicts with the requested no-foreground requirement if exercised; its runtime execution, success and visible effect are unproven.** Windows may deny a foreground request; that possibility does not establish this route meets the constraint. See Microsoft's [SetForegroundWindow documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow).

The candidate sender then calls `0x3940a60`, which reads `GetCommandLineW`, finds a quoted or unquoted executable prefix, copies the remaining text and passes it through `0x39424f0`; complete parsing and quoting semantics are not characterized. If the resulting string is nonempty, it calls `GlobalAddAtomW` and posts message `0x42a` with the returned atom through `0x3943f00`, whose ordinary branch reaches `PostMessageW`. A failed post leads to `GlobalDeleteAtom`. `PostMessageW` accepting a message does not establish that the receiver processed the file, and the Microsoft [GlobalAddAtomW reference](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-globaladdatomw) documents a size limit and failure return. Atom creation success and truncation behavior in this application are not established.

A decoded candidate window procedure `0x394ec00` branches on `0x42a`, retrieves an atom string using `GlobalGetAtomNameW`, deletes the atom, and, if nonempty, calls `0x3942720`. That helper handles a quoted string, calls `GetLongPathNameW` with a `0x104`-wide-character buffer, and invokes a receiver's virtual `+0x90` with the resulting buffer and return length. Receiver class and ultimate open action, error semantics, thread contract and ownership have not been proven. No direct invocation or fabricated message is warranted. The static sender/receiver protocol resemblance is evidence of a possible forwarding path, not runtime proof of delivery or successful project selection.

## Controlled second-process experiment: prerequisites and risks

The current repository launcher `native/CubaseDesktop.cs` starts a quoted executable and one quoted project on a private desktop, but its `Start` method owns one process and rejects a second call in the same holder. It records the active foreground handle before and just after launch only; equal snapshots cannot detect a transient foreground change, a prompt on the private desktop, or a project completion. Launching a second Cubase on the same desktop could hit the explicit foreground path above, switch active projects, show a dialog, change audio-bus connections, write project preferences or other files, load plugins, or leave a separate process running. A different desktop might instead produce a separate host, not a meaningful forwarding test. Treat these as unresolved risks, not asserted outcomes.

Therefore **do not run the second-process experiment under the existing no-foreground constraint**. A valid future design first requires a supported route or independently verified launch conditions that exclude the `SetForegroundWindow` branch without modifying Cubase, process memory, interface tables or licensing. If that prerequisite is established, prearm observation of original and candidate process IDs/start times and desktop, continuous foreground/event monitoring, private-desktop windows and prompts, distinct disposable CPR paths, current root and informer state; then issue exactly one documented launch request. Record before/after project file state and a host-owned completion signal, retaining unknown results when no signal exists. A window title, a second-process exit, a returned launch ticket, a successful post, or two foreground snapshots alone do not prove forwarding or success. If an observable dialog, foreground transition, unexpected additional host, missing evidence, or non-disposable target occurs, stop without input or retry. No evidence currently proves the prerequisite or supplies such a documented request.
