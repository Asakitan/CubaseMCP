# Architecture

```text
MCP client -> stdio SDK -> strict tool schema -> one MidiClient (parameter/control operations)
  -> exact named Windows MIDI ports -> no-window virtualMIDI loopback host
  -> bounded SysEx frames
  -> Cubase ES5 MIDI Remote driver -> controller -> documented host API
```

The return path carries correlated replies. There is no adapter router, foreground process controller, network service, synthetic state provider or command replay queue in the Node server.

Port-host startup starts independently without inherited response handles and waits for a matching PID readiness record followed by exact port enumeration, with a bounded wait. This applies before native project admission; it does not replay an operation.

The explicit project lifecycle uses a separate fixed native initializer on the owned event thread, not a retry/fallback for MIDI controls. See `docs/background-project-lifecycle.md`.

Session 31 adds explicit native operation 5 for audio export through a temporary NonUI host controller. `cubase_audio_export` no longer executes export-window commands; it passes an output path and sample options through the existing owned-operation coordinator, selects the host's main output, then reads the emitted audio metadata. Builds, three focused contracts and four different real-host format/rate/depth outputs passed; see `docs/native-file-services-31.md`.

Operations 6, 7 and 8 add explicit-path audio import, native event/note discovery and guarded event/note edits. `NativeProjectModel.h` traverses MIDI-part contents, reports temporary event IDs, and uses host getters/setters on the owned event thread. Note edits require exact identity and original values. The temporary context's working/start/end time bases agree, and time writes check the inverse conversion before entering a setter. Native sidecars carry the fixed operation parameters, not arbitrary addresses or executable commands. Final builds and 193 tests passed; audio/note readback and a fresh-process persistence check have separate live evidence.

Operations 9..12 cover track creation, plug-in unload, audio-bus routing and automation data. `NativePluginServices.h`, `NativeRouting.h` and `NativeAutomation.h` use the same owned event-thread dispatcher. Session 34 fixed Group/FX persistent recreation with a `VST Multitrack` factory token and the complete binding sequence, added real instrument/folder tracks and send destinations, and passed fresh-reopen semantic acceptance. Automation points have identity/count guards; output and send writes have independent MIDI feedback. See `docs/native-host-contracts-34.md`.

## State and Outcomes

Sessions 32/33 retain the failed track prototype and destroyed-track dumps at `Cubase+0x2e1bdb0`. Session 34 demonstrated why tree/mixer visibility alone was insufficient: reference paths and factory tokens have different reconstruction semantics. The corrected sequence passed the original failing reopen check and an extended instrument/folder/send/automation check in a new process, without a new crash dump. Historical receipts stay unchanged; current results are in `native-host-contracts-34.md`.

Host object IDs are not durable project identifiers. Discovery and mutation must use the same session and root. Mapping-page activation changes the session; removal callbacks revoke the affected observations. Runtime evidence is separate from protocol fixture evidence and static feature presence.

Every session-based operation checks the required bridge revision, host version, active mapping and session before dispatch, including the original discovery and mutation tools. An old controller returns `BRIDGE_UPGRADE_REQUIRED` before dispatch; a changed session returns `STALE_SESSION`. Status, capabilities and explicit connection reset report compatibility without performing host editing work. `cubase_capabilities` reads the owned-runtime inventory first and uses a bounded 2000 ms read-only handshake, returning `host: null` with an explicit `hostState` when no mapping answers; `cubase_status` keeps the configured budget. The doctor distinguishes MIDI/handshake availability from `readyForOperations`. This handshake does not reload a Cubase script.

Selected-track identity and runtime ID are read from the host before track control reads, feedback attribution and writes. A changed or unavailable identity clears cached track feedback; optional expected unique and runtime IDs reject writes to another observed selected-channel instance. Selected and bank insert-viewer on/bypass/automation and parameter writes require the current channel and observed plug-in identity in revision 3.9; malformed active callbacks revoke that identity. These checks are not atomic and callback provenance can remain uncertain. EQ, filter, send, instrument and five strip-slot bindings are obtained from the selected host channel. Send and cue-send counts come from the host with a bounded admission limit; unavailable branches are reported as errors. Meter controls are read-only. Control Room bindings use the declared root/main values and host-reported maxima for indexed groups, with a shared 16-channel admission budget; they are not evidence that the AI edition has those features.

The revision 3.8 source status is a compact handshake. Controls and control groups are independently paged with bounded page sizes, and descriptive metadata is bounded without shortening identifiers. `transport.get` reports available tempo/time setters along with observed callback values. Fixed selected-track and bank insert viewers expose read-only values and identity-guarded actions; eight mixer bank slots also bind basic controls, selection, filtering, EQ, sends, quick controls and instrument/strip values. Selected-instrument and bank instrument/strip parameter-bank writes and navigation require the exact single-control plug-in identity and current channel guards. Callback identity is not an atomic instance guarantee. Their live behavior is unverified. The controller emits a few lifecycle messages to Cubase's script console without request payloads or project contents; those messages are diagnostic, not a handshake.

An initial root discovery explicitly refreshes its DirectAccess snapshot. Parameter reads and child pagination do not rebuild it. Removal notifications revoke the removed object (or the root snapshot when its base is removed); ordinary change notifications preserve still-valid identities. Independent host-value callbacks supply control feedback. Native callback properties are written, never read back to copy a callback.

Parameter process/default values retain their native numeric range; reading them does not impose the normalized write range. Writes still validate their explicitly selected representation. The 3.8 edit-lock operation separately requires a discovered object/tag and matching `expectedLocked` before one DirectAccess setter call; its receipt is submission, not persistence or an atomic compare-and-set.

A mutation acknowledgement is not a transaction commit. The bridge reports host submission and available observations; timeout/cancellation after sending has an unknown outcome. A mutation timeout faults the channel. Only an idle read-only status miss is reported as `not_started` and drops the silent channel, so the next request opens the same two ports again; that request is never resent. Explicit reset opens a fresh channel without replay.

Every request carries a required epoch deadline. The remote checks it immediately before dispatch on the mapping page's documented `mOnIdle(activeDevice, activeMapping)` callback. Expired work returns `REQUEST_EXPIRED` without entering a mutation. Protocol and runtime queues have fixed capacities. Request-ID tracking fails closed at 4096 entries per page session; page reactivation is required before starting another session. Connection reset does not bypass that registry.

Transport tempo and locator calls use `mTransport.mTimeDisplay.setTempoBPM` and the requested primary/secondary `MR_TransportTime.setTime` directly. They do not substitute commands or open transport windows. Numeric and display parameter setters similarly use only the explicitly selected representation.

Cubase owns the project, audio thread and plugin lifecycle. This server does not emulate application features absent from the public API. A legacy core chain was verified on AI16.0.5 in an earlier process; session 24 subsequently verified the current revision's mapping, reads, and individual DirectAccess value and edit-lock round trips. A separate selected-track volume binding write remained unverified.

## Session 30: pages, confirmation and song tools

Controller 3.14 keeps three mapping pages: the main page (transport, selected track, quick controls, Control Room, all command bindings, DirectAccess), the mixer page (all `mixer.*` bank controls) and the minimal Save page. Feedback callbacks no longer walk the control table; observations carry epoch stamps and are invalidated by incrementing a counter. The reason is recorded in `docs/binding-root-cause-30.md`: a slow page activation is abandoned by the host and its surface values stop propagating. Activation counters are part of `bridge.status`; a page with host callbacks and no surface callback refuses writes.

The server adds a settle window to control and command writes and returns what the host confirmed. The MIDI client asks the bridge for a stored response when a reply does not arrive (`bridge.response`); it never sends the operation again, and a request that the same script instance never admitted is settled as not started.

Song-level tools sit on three host mechanisms: DirectAccess parameters of mixer channels and of the transport object, the key-command allowlist, and native lifecycle operation 4 (MIDI file import). MIDI content is read back from the file that Cubase writes for the project; audio is exported by the host's own export, started by two key commands, with the written file as the only completion evidence. A host window is never operated: unexpected windows are reported by a read-only inventory and the instance is replaced. See `docs/song-tools-30.md`.
