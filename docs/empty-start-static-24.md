# Empty-start feasibility: static evidence 24

## Scope and conclusion

This static study used existing evidence and the installed Cubase 16.0.5.174 x64 image (PE timestamp `0x6adf121b`, preferred base `0x140000000`). During this static slice no process was restarted or operated, no UI or host command was used, and no earlier unknown request was replayed. At that point a project-free startup and first-open state had not been observed. The original launcher supplies a CPR when no explicit project is passed (`template-startup-path.md`); a later session 24 diagnostic separately added and exercised no-CPR-argument startup and one first-project submission, with the measured limits documented in `first-project-open-24.md`.

## First-open activation branch

`0x1d437c9`–`0x1d437d8` in existing-project routine `0x1d42430` calls `0x279d940` on global `MProject` and branches around the activation-prompt construction when its signed return is at most 1. For the observed list interface, `0x279d940` dispatches `MProject+0x78` vtable `+0xd0` and the observed target `0x15e4310` reads the interface dword `+0x10`. A separately observed two-node list matched that field (`project-activation-predicates-22.md`, `project-list-22.md`). Thus a verified value of 0 or 1 at **this gate** skips this one prompt consumer; this is not a promise that an initially empty session stays at that value after a document is constructed or that the first open has no other prompts. The moved-directory dialog is a separate observed prompt for a different request, with an unproven connection to this hypothetical scenario (`project-moved-prompt-19.md`).

Project-selection routine `0x279e640` stores the new root at `MProject+0xf8` and subsequently dispatches listener slot `+0x18`; it returns early on the same-root comparison before the notification loop. Informer registration adds a listener but does not itself replay an existing root (`midi-project-notifications.md`). Those static facts make listener-before-first-selection a discriminating condition, not proof of a usable host-open contract. Existing prearmed startup captures all launched with a CPR: session 20 first observed root before informer, but polling leaves event order and missing callbacks unresolved (`midi-startup-timeline.md`). No identified code or observation establishes empty-command-line root/informer startup order.

## Hub and startup boundaries

In action-handler function `0x1d50ad0`, `0x1d514d8` loads ASCII `NewWithHub` at RVA `0x42ee1a0` into a string comparison. If the comparison returns zero, `0x1d51504` checks a local byte `r14b`; on its zero branch `0x1d5150d` calls `0x1ae0340`. That routine has multiple global/object null and state checks, and a virtual dispatch at `0x1ae04f0`. The action name and this conditional route do not prove that an empty launch invokes it, that Hub is shown, or how to disable it without changing state. The distinct `Open Hub On Close Project` literal at RVA `0x4259260` has an initialization-shaped reference at `0x129e1c4`; it alone does not prove current preferences or startup behavior.

Independently, the startup routine `0x1d551d0` conditionally calls Safe Start at `0x1d554b6` based on cached marker check or modifier state, subject to an earlier branch; marker state is cached. Empty command line does not establish those inputs or rule out this or other UI (`native-startup-contract.md`).

## Foreground and experiment boundary

The candidate existing-instance launch path `0x3940920` performs a handshake and, after a matching result, calls wrapper `0x3944120`; its normal branch reaches `SetForegroundWindow`, although its overall launch conditions, desktop scope and execution are not proven (`project-instance-routing.md`). Empty arguments do not establish that this pre-handshake call is avoided: argument-tail processing occurs later in that candidate path. Therefore a second-process launch cannot be assumed background-compliant, and no such launch is justified by the current evidence.

The static follow-up called for identifying the no-project startup decision and informer registration sites, then comparing root, list count, listener, informer tree and dialog/foreground samples around one distinct first-project submission. Session 24 subsequently added separate empty-start and transition modes and ran that comparison; it did not establish an authoritative project completion signal or continuous UI history. Polling is not an event log; all unknowns remain explicit. The existing two unresolved submissions were not replayed.

## Follow-up: first-open path to moved-project handling

On a successful path in `0x1d42430`, `0x1d4358f` loads `document+0x108` into `r15`, and `0x1d43611` calls `0x27e6300` with that pointer as RCX, the candidate path in RBX as RDX, `R8B=1`, and R9 pointing to a local mode dword. `0x1d435f5`–`0x1d43601` sets that dword to 1 exactly when the routine's saved incoming R9 pointer is non-null. Within `0x27e6300`, a non-null receiver and non-null result from `0x2758900` are prerequisites. At `0x27e6360` the local mode is read: mode 1 takes a different helper; mode 0 reaches `0x27e6394`, calling moved-project routine `0x2810150` with the `0x2758900` result, path, `R8B=1`, and `R9B=1`. The known `0x1d53d3c` existing-file caller passes R9=0. This is a newly established **conditional static connection**, occurring before the activation-prompt count test at `0x1d437c9`, not proof that any particular process or fixture reached it. The moved-project routine's further comparison `0x28104be` and other branches still govern its modal call; the meanings and equality of the compared path objects are not established. Therefore same-directory placement is no guaranteed suppression and a skipped activation prompt does not skip the moved-project path.

Root construction at `0x2754bdc`–`0x2754bf6` also invokes the MProject secondary interface slot `+0x30` with `root+0xa8`. The fixed secondary vtable `0x447d448` maps that slot to `0x180ec60`, which shifts the interface pointer by `0xb8` and dispatches the resulting subobject's `+0x28`; relative to the complete MProject object this is `+0xc8`, the separately documented listener container, not the project list at `+0x78`. This registration-shaped call must not be mistaken for a proven first-root list increment. No complete project-list insertion path or gate-time count on an empty-start first open has yet been established. The already launched empty instance's evidence is separate from this static tracing; no live count or open result is asserted here.
