# Project open options: fixed-image call sites 23

## Scope and reproducibility

This is a disk-only analysis of Cubase 16.0.5.174 x64, PE timestamp `0x6adf121b`, preferred base `0x140000000`; no process call, submission, target modification or UI action was made. To reproduce, scan executable-section bytes for `E8 rel32` whose destination is `0x1d42430`, then require Capstone x64 linear decoding from the containing PE exception-directory function start to identify the candidate instruction as a `call`. Eight sites survive this filter: `0x1d3a939`, `0x1d3a987`, `0x1d42efc`, `0x1d46932`, `0x1d46941`, `0x1d469e5`, `0x1d53b8d`, `0x1d53d3c`. This is not an exhaustive proof of callers: indirect calls, tail jumps, other modules, and code missed by linear decode remain outside scope. None is evidence of a call actually executed during the existing unknown submission.

## Follow-up: path construction and indirect-slot provenance

At `0x1d424c9`–`0x1d424f1`, non-null input `RDX` is retained in `RDI`, `0xe8` bytes are allocated, and `0x3b0c8b0` is called with `RCX` equal to that allocation and `RDX=original RDX+0x10`. On successful allocation, its return becomes `RBX`. That constructor calls `0x3b14f90` with the incoming arguments and then installs primary and secondary vtables `0x4831bc0` and `0x4831d70`; the primary RTTI is `Steinberg::FNPath`. In the base routine, the consumed interface's virtual slots `+0x40`, `+0x18`, and `+0x58` are called; their results are used during path-field construction. This establishes construction from a path-shaped interface, not the resulting path content, normal operation completion or lifetime contract. `0x1d42525`–`0x1d42593` may use a helper and replace `RBX`; allocation failure or a null result bypasses the `RBX != 0` branch. Between the explicit store at `0x1d4259c` and the prompt gate, linear decoding finds no other explicit `[rsp+0x50]` write, though aliases and non-linear paths are not excluded.

A bounded raw-byte scan for indirect `call`/`jmp` with displacement `+0x1b8`, checked by linear decode from PE function starts, yields many unrelated polymorphic calls; a slot offset alone does not identify an application receiver. Two instructive candidates in `0x36cbd50` are `0x36cc0f7`, supplying `R8=0`, and `0x36cc54f`, supplying `R8B=1`; both use the function's incoming `RCX`, retained in `R12`, as the receiver. `0x36cd3d9` similarly calls with `R8=0` using incoming `RCX` retained in `RBX`. RTTI and tables place `0x36cbd50` at `GApplication` primary vtable `0x471fa40 +0xb0` and `0x36cd3b0` at `+0x178`; that static GApplication table's own `+0x1b8` is `0x36ccc90`, not `0x1d53b10`. The PCubaseApplication primary table's corresponding `+0xb0` and `+0x178` point to different methods. A dynamic PCubase receiver reaching those inherited bodies is not established, so none of these sites is a confirmed caller of `0x1d53b10`.

Other candidates `0x366f23d`, `0x366f262`, `0x366f61a`, and `0x366f87d` use entry receiver saved in `RBX` or `RSI`; the first pair pass zero and one respectively, the latter two pass one. Table/RTTI checks place `0x366f4d0` in `PCompTool`, `GSelectTool`, and `AXtTool` vtables, not an established PCubaseApplication receiver. Calls from that function to `0x366f200` preserve its receiver. These are leads only, not proven application calls. The scan covers an encoding subset, not all indirect dispatches.

Even a valid alternative path through `0x1d53b10` calls the much larger `0x1d42430` and therefore has no demonstrated complete no-prompt property. Separately, `project-moved-prompt-19.md` documents an observed private moved-project prompt for a different unknown request and its static literal/conditional modal routine `0x2810150`; the relationship of that specific prompt routine to this alternate entry has not been proven. There is no basis to infer that suppressing the activation consumer avoids that or other dialogs.

## Revert route: action delegation and mandatory confirmation branch

The derived `PCubaseApplication` vtable `+0xb0` targets `0x1d50ad0`. That function retains incoming receiver and action in `r12` and `r15`, and directly delegates both to `GApplication` handler `0x36cbd50` at `0x1d5151f` on one branch and `0x1d52e89` on its fallback branch. This establishes possible derived-to-base delegation while preserving the derived receiver; reachability of either branch for a particular submitted action and its dispatcher/thread are not established. In the base handler the action is tested against `Interpret` and `CanInterpret`; `0x36cc020`–`0x36cc02f` sets `SIL` from the latter test, and the `Revert` action name is checked at `0x36cc3aa`–`0x36cc3c3`.

On the Revert branch, the receiver's virtual `+0x1c0` obtains a document candidate, and its virtual `+0xe0` obtains another pointer in `r13`. After non-null checks, `0x36cc410` tests `SIL`: nonzero goes directly to `0x36cc593`, skipping the open dispatch. If `SIL=0`, the code constructs a UI request and invokes its provider at `0x36cc4be`; only result dword 1 reaches `0x36cc525` and then `0x36cc54f`, which calls receiver vtable `+0x1b8` with `RDX=r13` and `R8B=1`. Thus the identified `CanInterpret` route does not silently reach that call; the interpret route visibly calls a provider first. Provider implementation and precise button meaning are not proved. After a non-null returned pointer, `0x36cc567`–`0x36cc56d` calls the old document's virtual `+0x108`, whose effects are unresolved. The Revert operation may replace or close existing document state; neither the confirmation nor this method is appropriate to invoke against the pending unknown submission. This route is not a proved unattended open or safe activation API.

## PSS VA clone: independent design review

Microsoft specifies that `PSS_CAPTURE_VA_CLONE` includes cloneable private and shareable mapped/image pages, and documents optional/normal/force breakaway behavior for jobs; force breakaway requires TCB privilege. These rules do not prove how the current restricted job will behave or that all mappings and captured thread contexts form a globally atomic state. See [PSS capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags) and [PssCaptureSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot). The current handoff reports UI and lifetime job restrictions and a pending prompt; the most recent synthetic-only run in `project-activation-clone-22.md` reports a successful bounded named-frame unwind and one subsequent process-inventory absence observation, not complete resource reclamation or target compatibility.

This review called for current target/job identity and limits, resource and timing bounds, a restricted synthetic-job experiment, and a cleanup plan that never closes the original holder/job handle. It also identified copy-on-write pressure, mutable shared pages, unspecified scheduling impact, races and captured-thread privacy as limits. No breakaway was assumed. The subsequent fixed-target capture, its partial stack, actual preflight thresholds and unresolved guarantees are recorded in `project-activation-clone-23-target.md` and `project-activation-stack-23.md`; no host operation, dialog input or target memory write was performed. The trace does not identify a prompt decision or completion of either unknown open.
