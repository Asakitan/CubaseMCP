# Project Component Admission: Static Findings

Target: installed Cubase AI 16.0.5 on Windows x64. All addresses are executable RVAs for this build. This investigation reads files only; it neither loads a component nor alters process state, component admission or product configuration. `scripts/service-admission-inspect.py` reproduces bounded disassembly with `pefile` and `capstone`.

## Gate identity and implementation

The project factory's host-context query uses raw IID `c7 dc eb ad 94 44 0b 43 ab 1c 9a 17 4c e0 06 f5`, as recorded in `native-factory-recovery.md`. The identical initialized bytes occur in the executable at `0x426ebd0`. Query-interface implementation `0x1abcd10` compares that IID and returns its current secondary interface. Its vtable is at `0x426ebb0`; its MSVC complete-object locator at `0x4af0c50` identifies `Steinberg::FeatureDefs::ComponentChecker`, complete-object offset `+0x08`. Slot 3 is `0x39b36d0`; slots 1 and 2 return the constant `0x3e8` in this build.

The slot 3 implementation receives a component identifier in `RDX` and an integer threshold in `R8D`. It initializes a temporary identifier via `0x185e490`, iterates the checker's record array with stride `0x20`, compares the copied record identifier with the argument, requires record field `+0x18 >= R8D`, and tests record field `+0x1c` against the checker's mask. It returns zero when a matching eligible record has a nonzero masked bit; otherwise it returns one. This is a component/feature admission decision, not merely a generic context pointer assignment. The exact legal or licensing meaning of individual bits is not established and is not changed here.

## Normal data path and diagnostic boundary

The checker singleton's complete object is at executable RVA `0x58af130`; the queried interface is at `0x58af138`. Getter `0x1d3a030` initializes and returns the object. Call site `0x2f36f62`–`0x2f36f80` retrieves a pointer from its input object via `0x1c80010`, reads two 32-bit fields from that input at `+0x3c` and `+0x40`, and calls the checker's setter `0x39b3780`. The setter stores the pointer, count and mask at complete-object offsets `+0x10`, `+0x18` and `+0x1c`, respectively. Their origin, synchronization, exact record ownership and edition mapping are not yet established.

The host's normal module path and factory3 context delivery are described in `host-registry-access.md`: if admitted, a project factory receives the normal host container and tests its CID through this checker. The existing independent probe's zero public count was measured without host context and does not establish the checker's live decision. The real isolated host snapshot reports a null project-service cache and the component absent from its module list; these observations do not establish why the component was not loaded or whether the installed edition admits it.

A bounded read-only snapshot in the then-live PID 66528 inspected the existing singleton's array and mask without calling the checker or changing it. The header was unchanged across the read; of 321 records, the project CID occurred at index 37 with threshold 1 and record mask 15, while the host mask was 16. The observed bitwise match was zero for the factory's requested threshold 1. Evidence: `artifacts/native-probe/feature-admission-66528.json`. This supports the observed admission mismatch, but the snapshot did not lock the live array or prove the reason the component was not loaded. The process has since exited. No verified ordinary activation call or project CRUD operation has been recovered yet.
