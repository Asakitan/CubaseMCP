# Native project probe (diagnostic only)

This one-shot DLL is diagnostic scaffolding, not an MCP backend. It is built for the installed Windows x64 Cubase 16.0.5 profile only. Loading a DLL into Cubase is a separate invasive action and is not performed by the build script. The fixed, explicitly approved loader is documented in `docs/native-probe-loader.md`.

`StartProbe` is an exported `DWORD WINAPI StartProbe(void*)` entry; `DllMain` only records the DLL handle. One invocation pins the DLL for the process lifetime and starts one worker. The worker checks the executable name and version, PE machine and timestamp `0x6adf121b`, image bounds, and the container and project-host vtables before querying the fixed observed IID through the container. It releases the returned reference only when the returned pointer equals the expected host. It then checks the dispatcher holder at `0x5890930` and, if non-null, submits exactly `{"payload_version":"2026.10.01","command":"GetMusicalTrack","type":"Tempo"}` once.

The callback vtable is a deliberately limited C-style thunk for observed direct calls, not a claim of the complete vendor ABI. Unknown interface queries return no-interface. Atomic references keep its event and storage alive after worker timeout if the host retains the callback. Response bytes are synchronously copied while borrowed, at most 1 MiB, and protected against invalid addresses. A manual-reset event waits up to 20 seconds **after the request call returns**; the request call itself has no demonstrated bounded duration. Request and callback IDs must match before response text is emitted. Callback thread ID and immediate return are recorded; the immediate return alone is not success.

The dispatcher non-null check is only a snapshot: concurrent changes could still cause the host to take its inline path. Its dispatch target, thread affinity, shutdown synchronization, nominal callback IID and full ABI remain unverified; see `docs/project-host-abi.md`. The check is not a guarantee of main-thread execution or process safety. No automatic retry occurs. The DLL is pinned because host callbacks may arrive after timeout; the loader must not attempt to unload it.

The result is written to `result-<PID>.json` next to the DLL through a new temporary file and non-replacing atomic rename. Existing results are not overwritten. JSON includes process ID, verified executable name or null, profile match, stage, query result, host match, request submission, immediate return, request and callback IDs, and callback thread ID. `responseText` appears only for a correlated copied response. `StartProbe` returns 0 when the worker was launched, 1 if pinning or worker creation failed, and 2 for a repeated invocation; 0 is not project success. Subsequent host and timeout outcomes are available only in the result file.

Build with `powershell -NoProfile -ExecutionPolicy Bypass -File scripts/Build-NativeProbe.ps1`. It invokes the installed Visual Studio 2022 x64 environment, runs a syntax-only check before one DLL build, and places the output under `artifacts/native-probe`. In isolated PID 66528 the request-capable revision acquired the host, submitted the fixed query and received a correlated `host_error_callback`; it did not return project data. Evidence: `artifacts/native-probe/loader-66528.json` and `result-66528.json`. A compile or submission does not prove the complete native ABI or host behavior.

## Path-service lookup diagnostic

The session 14 image also exposes the fixed `StartPathProbe` entry, selected only by `scripts/Invoke-PathServiceProbe.ps1`. Its entries share a one-shot guard: only one worker may be started from that image in a process. The path worker checks the same host profile, the static `IHostClasses` subobject and its slot, the path IID and registered factory record, and the current class-factory vtable. It calls that host-class lookup exactly once with the fixed path IID, checks the returned interface vtable against the statically recovered `FNPath` secondary vtable and calls its observed release slot only on an exact match. A structured-exception guard records exceptions; an unexpected object is not released through a guessed slot. This creates and releases a temporary host object: it does not call its path setter, query or alter project data, submit an open/save action, use a dialog, or introduce an MCP backend. It runs on its diagnostic worker thread; the method's general thread-safety and the worker's suitability for any project operation are not established.

The worker emits `path-start-<PID>.json` before the lookup, including its thread ID, and a separate `path-result-<PID>.json` afterward, through non-replacing writes. A start record is not a completed lookup, and an entry return of zero means only that the worker was launched. A missing result must not trigger a replay. An exception, mismatched vtable, nonzero lookup return or missing object is reported explicitly; a normal release return is not independent proof of destruction or of project readiness.

In the owned private PID 39068, the loader returned `submitted` and entry return `0`; worker thread 39876 then reported `callResult:0`, a non-null object, matching vtable and `releaseAttempted:true`, with `stage:release_returned` and no exception (`artifacts/native-probe/path-loader-39068.json`, `path-start-39068.json`, `path-result-39068.json`). The process remained responsive at the immediate check. This is a successful scoped path-service lookup and release call, not a project-open/create/save/edit result. The previous built module was preserved in `artifacts/runtime/before-path-service-probe-5512a180349d4b27b4655fa91d72fbba` before rebuilding; the new DLL remains pinned in that process.

## Temporary Unicode path-object diagnostic

`scripts/Build-PathRoundTripProbe.ps1` builds the same source into a separately named fixed image, `artifacts/native-path-roundtrip/CubaseMcpPathRoundTripProbe.dll`, without overwriting the prior pinned image. Its `StartPathRoundTripProbe` entry is selected only by `scripts/Invoke-PathRoundTripProbe.ps1`. The image has its own one-shot guard. It validates the host profile, context and path-class registry, the expected `FNFileSystem` singleton and root-check slot, and the returned `FNPath` primary and secondary vtables before calling the path setter once with a fixed, synthetic UTF-16 absolute path and mode `0`. The fixed path is a diagnostic fixture, not a project to open. The worker then reads only the temporary object's bounded directory and filename string fields and calls the known release slot. It does not call a path getter, host-open method, project operation or UI action. A structured-exception guard reports an exception without replay; unmatched object vtables are not released through guessed methods. This changes a temporary in-process object but does not establish general thread safety or project lifecycle behavior.

In isolated PID 39068, worker thread 38096 reported lookup and setter returns `0`, matched primary/secondary vtables, wide directory and filename fields matching the fixed input, and a returned release call without exception (`artifacts/native-path-roundtrip/roundtrip-loader-39068.json`, `roundtrip-start-39068.json`, `roundtrip-result-39068.json`). The launch command checked that the synthetic CPR path was absent both before and after, and Cubase remained responsive immediately afterward. This is a setter plus direct field comparison, not a public getter round trip, canonical filesystem identity, project creation or open/save evidence. The separately named diagnostic image is pinned in this process; no automatic retry or replay occurs.
