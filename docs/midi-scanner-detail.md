# MIDI scanner detail: bounded static follow-up

Scope: Cubase AI 16.0.5 Windows x64, PE timestamp `0x6adf121b`, disk-only analysis. The separately recorded PID 3720 observation is in `docs/midi-informer-source.md`; this slice did not read or alter a process, configuration or UI.

Scanner method `0x22d4af0` compares two sequences of 0x88-byte records at scanner `+0x358` and `+0x370`. It counts entries whose `+0x60` and `+0x68` pointers differ in each sequence. A count difference reaches the notification loop at `0x22d4db8`; when counts agree it compares corresponding records' four string-like fields at `+0`, `+0x18`, `+0x30`, and `+0x48`, with special-case filtering of particular string constants. A detected difference also reaches that loop. It invokes slot `+0x10` on entries of a global listener array, passing scanner `+0x358`. The informer listener and its `>=5` byte gate are independently traced in `docs/midi-informer-source.md`. This is a concrete record-change notification path, not a description of how the details were originally populated.

The equality test in `0x22d4af0` only establishes whether a detail range is empty; `0x25afff0` separately requires a byte extent of at least five. The point-in-time empty detail vectors would not meet that later gate if passed unchanged. Neither empty details nor this static path identifies the missing producer, its Windows MIDI source, the meaning of detail bytes, nor whether the listener was notified for the snapshot.

Static inspection of code using offset `+0x358` must account for different receiver types: for example `0x22d4f70` uses `+0x358` on an object created by `0x22bdd80`, not on the scanner established above. Offset coincidence alone is not a producer identification. The exact constructor and assignment of the scanner records' detail vector, and a standard headless remediation, remain unresolved. The next discriminating static task is to follow scanner-specific callers that assign or copy 0x88-byte records into `scanner+0x358`, then identify the API that fills the source record's `+0x60` byte vector; a bounded live snapshot is useful only once its source layout and owner are proved.
