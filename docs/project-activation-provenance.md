# ActivateProject producer provenance

This is a static, read-only inspection of the installed Cubase AI 16.0.5 x64 executable (timestamp `0x6adf121b`). RVAs and RTTI are build-specific implementation evidence, not an exported interface. No process, user interface, license or project was modified. `scripts/project-activation-provenance-inspect.py` verifies the PE profile, requires each disassembly start to be a runtime-function begin, and decodes forward before printing the relevant ranges and RTTI-backed vtable slots.

## Receiver and a distinct producer

`0x1d1e0c0` is slot `+0xb0` of the primary RTTI-identified `Steinberg::PArrangeController` vtable `0x42ddfd8`. In its `ActivateProject` branch, the receiver's `+0x1a8`, then that object's `+0x108`, supply the root to `0x279e640`. The branch sets the return value to `1` after the call rather than forwarding the selector return; this value alone is not proof the selector succeeded or listeners were notified. The runtime sender, receiver ownership and dispatch thread remain unresolved.

A separate cluster uses the same literal. In the constructor at `0x1ddac80`, after a conditional non-null result at `0x1ddb502`, `0x1ddb544` constructs a `0x40`-byte object using `ActivateProject` and submits it, the receiver, `r9b=1` and an additional stack value `3` to `0x3a8d370`. At `0x1dde820`, an RTTI-identified `PRemoteWheel` secondary-vtable slot `+0x18`, a related object is built and submitted with the same apparent argument pattern after storing incoming `rdx` in the parent object at `+0xb8`. The `PRemoteWheel` primary-vtable `+0xb0` target `0x1dde420` recognizes the same literal and includes a state-dependent re-submission at `0x1dde74f`–`0x1dde779`. These are actual static producer sites; the shared literal does **not** prove they produce the `PArrangeController` input, nor that `PRemoteWheel` selects a project. Context and targets are different and their object types and lifetime contracts are not fully recovered.

`0x3a8d370` is a jump to `0x3a8c770`. On one path that helper stores the incoming object, receiver and fifth argument in an allocated record and calls `0x3ab9330` with a queue-like member at helper receiver `+0x20`. Other branches include an early path. This establishes a deferred-record-shaped mechanism, not its actual scheduling, delivery, thread affinity, ordering or completion. Neither a main-thread guarantee nor a safe callable interface follows from it.

The PE literal scan used RIP-relative `lea` byte candidates, mapped each to its enclosing runtime-function range and verified decoding from that function's start. It found one arranger comparison and four references in the remote-wheel cluster above; this is a bounded inventory of that encoding in this executable, not proof of all string uses, other modules, indirect sources or runtime execution.

## Public documentation and discriminating next step

Steinberg's [Cubase 15 Project Window Toolbar documentation](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/project_window/project_window_toolbar_r.html) describes a user-facing Project Activation Control, available when a project is inactive or multiple projects are open. Its [opening-project documentation](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/project_handling/project_handling_opening_project_files_t.html) says opening an additional project can ask whether to activate it. These version-15 Pro descriptions do not establish the internal command's source, AI 16 behavior or background automation. The official [MIDI Remote command-binding example](https://steinbergmedia.github.io/midiremote_api_doc/examples/commandbindings/) lists Cubase/Nuendo 13 commands such as File/Open and Save, but no exact `Activate Project` entry was found in that published page; this is not proof of absence from AI 16. The documented examples do not establish project-path arguments, no-dialog behavior, mapping availability before an active project, or completion.

Next inspect the `0x3ab9330` queue object's concrete implementation and its consumer, prove whether the record is delivered to `PRemoteWheel` or an arranger receiver, and identify object lifetime and execution thread from a normal proven call chain. In parallel, identify a supported source of two different already-open roots and a documented, prompt-free selection interface; the public toolbar description does not meet that requirement by itself. A later controlled observation should separately record old/new root identity, post-registration listener membership, prompt state and a completion signal. Equal-root no-op, an unavailable mapping and a different-root event with no informer insertion are distinguishable outcomes; no experiment or success is asserted here.
