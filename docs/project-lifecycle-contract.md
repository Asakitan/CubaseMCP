# Project and MIDI lifecycle contract investigation

Target: installed Cubase AI 16.0.5 Windows x64. This note combines static investigation with separately identified bounded read-only snapshots; it is not a supported SDK, a client ABI, or evidence of a successful host operation. Addresses are RVAs specific to this installation. No lifecycle method was invoked and the snapshots did not modify Cubase.

## Project lifecycle

The existing `projectplugin.dll` request parser dispatches `ExportMix`, `CreateTracks`, `Transport`, `Locators`, and `GetMusicalTrack` as documented in `docs/host-project-api.md`. Its observed dispatch table is not a new/open/save/save-as project contract. Component export or creation of a project service object does not establish a live project owner, native main-thread access, project lifecycle arguments, or disk persistence.

The executable RTTI `SkiProjectController` has a complete-object vtable at `0x42df078` and secondary vtables at `0x42df0f0`, `0x42df118`, `0x42df148`, and `0x42df170`, with secondary offsets `0x10`, `0x18`, `0x20`, and `0x28`. Slot targets can be inspected with `scripts/project-lifecycle-inspect.py`. Their signatures and association with project creation or saving remain unproven. Treating an RTTI name or slot location as a lifecycle API would be speculation; no method here is exposed to MCP.

`scripts/project-lifecycle-v2-inspect.py` reports bounded references to `CreateNewProject`, `openProject`, `CreateDocument`, and `SaveDocument`. These are distinct leads, not a complete scan: it covers selected RIP-relative instruction encodings and rejects references that do not align with a decoded runtime function.

#### Derived application dispatch and path extraction

Static follow-up resolves the global pointer at `0x5972e30` to the application object: `UApplication` constructor `0x362fde0` stores its `this` pointer there at `0x362fece`, and the destructor clears it at `0x3630152`. RTTI identifies primary vtables for `PSequencerApplication` at `0x42eba20` and `PCubaseApplication` at `0x45d07a0`. In both static derived vtables, byte offsets `+0x168` and `+0x170` point to `0x15cb310` (`xor al,al; ret`). Thus the previously identified `CreateDocument` and `SaveDocument` abstract dispatch branches do not themselves establish working create/save implementations for those static derived vtables. A subsequent runtime application-vtable observation is described below; it remains an unlocked observation of one process at one instant.

The `openProject` action handler at `0x2900aa0` retrieves a `path` field via its action object's subobject at `+0x18`, checks the retrieved object's type against the string `FPath`, and, only on success, invokes application vtable byte offset `+0x178` with `RDX` equal to that object and `R8=0`. Both derived vtables select `0x1d53bb0` at this slot. That method keeps the incoming object in `RSI`, may retain and put it into an action container, and follows multiple state-dependent branches; one calls `0x1d42430` with the path-like object, two zero register arguments and a fifth stack argument of one. A return byte is observed, but precise meanings, `FPath` construction and ownership, execution thread, dialog branches and completion are not recovered. A valid path string is not interchangeable with this object. This is a concrete open candidate, not a verified no-dialog API or file-open result.

The generic `SaveDocument` dispatcher obtains an action parameter named `Path` through its `+0x18` subobject and one named `Document` through its `+0x10` subobject before the vtable `+0x170` call. Their class identities, construction and ownership remain unknown, and the resolved static derived slot is the no-op described above. The search for actual project save and save-as must continue in the document/project implementation rather than invoking this abstract slot.

#### Existing-path Save action

The actual `Save` action follows a different branch of the dispatcher. Comparisons at `0x36cc20e` and `0x36cc22d` recognize `Save` and `Save New Version`; both reach `0x36cc5f4`. The branch records whether the action is `Save New Version`, obtains a current document via application vtable byte offset `+0x1c0`, and checks document vtable offset `+0xf8`. It also tests a separate global-object condition through vtable offset `+0x3a8`. It obtains the document's current path through its vtable offset `+0xe0` and retains the returned object.

When the current path is non-null and the action is not `Save New Version`, the control flow skips `0x36cc6c0`–`0x36cc755`, a path-acquisition branch which calls `0x36cd680`. At `0x36cc8da` it then calls the application at vtable byte offset `+0x1c8` with `RCX=application`, `RDX=document`, and `R8=0`. In both static `PCubaseApplication` and `PSequencerApplication` primary vtables these offsets resolve to `0x1d3a220` and `0x1d57900`, respectively. This is distinct from the unrelated no-op `SaveDocument` slot `+0x170`.

At `0x1d57900`, a null or non-`FNPath` third argument makes the method obtain the document's current path through `+0xe0`; a missing path fails. The document is then checked by type name: `PSkinDocument` takes `0x15f6660`, while `PArrangement` transfers to `0x1d579d0` with the document and path objects. That latter routine performs extensive state, path, file and object checks before further work. The source-level method names, document ownership, exact dirty check, returned boolean meaning, disk-completion semantics and required thread are still unverified. Skipping the dispatcher path-acquisition branch is concrete evidence for one existing-path route, **not** proof that lower-level checks never show dialogs or that a project has been persisted. No save call was performed.

Within the arrangement-save routine, `0x1d58532` selects one of two serialization paths based on a local state byte. One branch constructs a stream-like wrapper at `0x3b38db0`, then an object at `0x3b234c0` whose `+0x18` field holds the passed stream pointer. The caller adds objects under the strings `Version` and `Project` at `0x1d58594` and `0x1d585a7`, with the `PArrangement` document passed for the latter; other conditional entries include `Devices`, `WindowLayouts`, and `ProjectLayouts`. It calls `0x3b2b930` with `SteinbergProject` and records its byte return. An alternate serialization branch references `Arrangement1` and other entries. These are concrete serialization-path observations, not direct evidence of a successful operating-system file write, flush or atomic replacement.

Near the end, `0x1d58d4b` tests an internal status byte. A failure path calls `0x1d562b0`; for status `-0x60`, if that helper returns true, it recursively invokes `0x1d579d0` again. A separate success path sets `BL=1`, and the method ultimately returns that byte in `AL`. Error mapping, the helper's UI behavior, the meaning of individual state bytes, durable write completion and the thread/dispatch contract remain unrecovered. In particular a controlled single-call test could trigger internal retry or UI even with a previously known path; do not interpret the existing-path branch alone as a no-dialog guarantee. The next static step is to identify the concrete stream destination and error-helper behavior for that branch, then determine a host-owned safe execution context. Only after those are known should a copied-project test record pre/post disk state and semantic reopen evidence.

The smallest read-only follow-up is to inspect the real application vtable and separately recover the documented lifetime and concrete current-document type through existing host facilities; a pointer snapshot alone does not authorize invoking these methods. Establish host-thread dispatch and prompt behavior against a copied project before any write experiment.

For `PArrangement`, RTTI identifies primary vtable `0x42d96c0`. Its slot `+0xe0` resolves to the leaf `0x15f5de0`, exactly `mov rax,[rcx+0x30]; ret`; its slot `+0xf8` resolves to `0x15ce3b0`, which always returns true and therefore is not an observed dirty-state test. Subject to first verifying that the live document's primary vtable actually equals the `PArrangement` vtable, a bounded read-only inspection of document `+0x30` yields the same path pointer as that leaf getter. `FNPath` and `FPath` static primary vtables are `0x4831bc0` and `0x4832b20`; unknown derived objects must not be assumed to share the layout. The FPath input-string field is at object `+0xc8`; its UTF-16 storage pointer is at `+0xd0` and the low 30 bits of the field at `+0xd8` encode length. That field records path text and is not, by itself, proof of canonical disk identity. Reads require a lifetime/synchronization strategy and a conservative length bound.

The application's current-document function `0x1d3a220` is not a simple field getter: it begins with the global pointer at RVA `0x5973480` and calls `0x363a900`, explores context objects, uses virtual calls and type checks, and can traverse multiple candidates. `0x363a900` delegates to `0x363a260` with a constructed local predicate. The latter uses the global object's `+0xe0` subobject's virtual `+0x138` to create an iterator, iterates elements and invokes the predicate until a match, then destroys the iterator. This is not a recovered fixed-offset current-document field. No complete non-invoking current-document pointer chain or stable synchronization contract has yet been established. Subsequent bounded candidate document and path reads are recorded below. The lower-level arrangement-save method `0x1d579d0` includes multiple file and global-state branches; its synchronous/asynchronous completion and error contracts remain unproven.

The manager constructor `0x3637920` installs vtable `0x4192350` in its `+0xe0` list subobject. Its iterator-creation slot `+0x138` is `0x3a88320`, which initializes the iterator's current node from subobject `+0x18`, i.e. manager object `+0xf8`. Iterator method `0x3a889a0` returns the current node's value at `+0x08` and advances to the next pointer at node `+0x00`. These are linked `{next, value}` nodes, not direct document pointers. The predicate used by `0x363a900(manager, 0)` is `0x1ca28e0`: it checks the `UWindow` type and compares the window's virtual `+0x398` result with zero. Thus selecting the first node is not equivalent to selecting the document. Once a window is selected, `0x1d3a2c5` calls leaf getter `0x15f5e30` to read `window+0x48`; the result undergoes interface query, type checks, and additional selection paths before a document is returned. A bounded read-only list traversal can record node pointers, value pointers and observed vtables, but must detect cycles and guard against concurrent changes; it must not label a candidate as the active document without reproducing the complete selection semantics.

#### FPath creation and diagnostic limits

RTTI identifies `Steinberg::FPath` with primary vtable `0x4832b20` and secondary vtable `0x4832cb0` at complete-object offset `+0x10`. Function `0x3b15e70` allocates `0xe0` bytes through the executable's allocator, initializes both vtables and a reference count of one, and returns the complete-object pointer; its observed body consumes no input arguments. The primary vtable's byte offset `+0x10` is release thunk `0x15c31c0`, which jumps to `0x3b89d20`. Allocation and release belong to the same executable runtime, not an external allocator. Full destructor semantics and failure handling remain unverified.

Primary vtable byte offset `+0x178` targets `0x3b16d30`. Its observed inputs are `RCX` complete object, `RDX` path text pointer, and `R8W` an unidentified path-type field. It copies the string into the object's field at `+0xc8` and calls virtual offset `+0x180` with the same text; a true result sets the type field at `+0xc2` to one. The string helper `0x3b7f020` scans successive 16-bit code units to a zero terminator, establishing UTF-16 code-unit input. The meanings of path-type values, normalization, return status and error handling are not yet established, so this is not a stable portable SDK contract.

Another complete-object constructor, `0x3b15290`, consumes a UTF-16 text pointer in `RDX` and a 32-bit type argument in `R8D`; it initializes and copies that text into `+0xc8`, then performs a virtual `+0x180` check. Call site `0x15f69e1` supplies value `1` and the one-character UTF-16 string `\`, loaded from RVA `0x4832a1c`. The constructor's own branch at `0x3b15389`–`0x3b153e5` sets the type field to one for that same one-character root case. Two other constructor sites, `0x354e331` and `0x3b43c33`, pass type value `0` with runtime-derived text. These examples do not prove a general file-versus-folder enumeration or the correct value for an arbitrary absolute project filename. The object is `0xe0` bytes in the allocation path; stack construction requires matching this executable's own destruction and alignment conventions, not guessed external structure fields.

The static derived `PCubaseApplication` vtable is `0x45d07a0`; a future read-only diagnostic can compare the actual non-null global application's first vtable pointer to image base plus that RVA and report the observed slot `+0x178`, without calling it. This observes dynamic type only at that instant and does not establish lifetime or thread safety. `0x1d53bb0` may build an `OpenFile` action with fields named `Path` and `ProjectDir`, submit it when particular global flags are set, and then continues through further branches. It separately tests the input against `FNPath` at `0x1d53c8e` before an existing-document path. The action submission is conditional and is not evidence that all branches dispatch to the main thread; the ordinary file-processing path has no proven dispatch-to-main-thread guarantee. State-dependent operations may present UI, and their dialog behavior remains unresolved. The smallest subsequent execution investigation must first establish the host's actual lifecycle-thread dispatcher and a demonstrably prompt-free path on a copied project; no such execution is justified merely by matching the vtable or constructing an `FPath`.

### Project service lookup diagnosis

The host's service cache lies at complete `ProjectPluginHost` object `+0xf8`. Its request path looks up a component when the cache is null. Executable initializer `0x1378640` constructs the lookup key at RVA `0x58d18b8` from the same class CID as the project component (`81 18 fa 7c 4d e5 50 4e 8a 01 de 63 b1 64 f7 42`). Request entry `0x1dd04cc`–`0x1dd04f8` calls `0x3aa5d80` using the manager pointer stored at RVA `0x599ca30`, then queries the returned object for the service IID. Lookup walks the manager's pointer range at offsets `+0x28` and `+0x30`, compares each record's CID at `+0x28` and `+0x30` with the key's two identifier words, and returns the matching record's pointer at `+0x10`.

The subsequent request work body calls the begin-like callback only if the cached service is non-null; a null cache takes the error path without a service request. A begin event followed by an error instead indicates that the service path was entered and returned a nonzero result. Callback observation and cache inspection must be interpreted together, and a concurrent registry traversal requires its actual synchronization contract. The normal `FModule` factory-context delivery and class-enumeration path are documented in `host-registry-access.md`; the key match alone neither proves that component activation occurred nor justifies fabricating context or modifying registration.

Steinberg's [VST 3 documentation](https://steinbergmedia.github.io/vst3_dev_portal/pages/Technical%2BDocumentation/API%2BDocumentation/Index.html) describes host persistence of plug-in component and controller state, not a demonstrated external Cubase project lifecycle interface. Plug-in `getState`/`setState` is not evidence that a complete project was saved.

## MIDI device notification and script reload

The executable's ASCII `USB Change Listener` string is at RVA `0x45d1b00`. A RIP-relative reference in the window class setup function `0x2f400a0` associates it with a window procedure at `0x2f401e0`. In that procedure, `0x2f40203`–`0x2f4021c` effectively compare the message to `0x219`, and `0x2f40222`–`0x2f40229` compare `wParam` to `7`. The matching branch calls a virtual method on a global object if non-null and conditionally invokes another function with `0xfa0`. Its callback identity, timing semantics, device enumeration effect, thread ownership, and relationship to MIDI Remote activation have not been established. The branch does not read `lParam` before those calls.

Microsoft documents [`DBT_DEVNODES_CHANGED`](https://learn.microsoft.com/en-us/windows/win32/devio/dbt-devnodes-changed) as a system-broadcast `WM_DEVICECHANGE` notification with `wParam` `7` and `lParam` zero for changes to device nodes; it recommends refreshing device lists. This describes the event, not a guarantee that creating virtualMIDI endpoints generates a devnode change, that an application-posted message has identical semantics to a system broadcast, or that Cubase reloads MIDI Remote scripts in response.

The executable also contains RTTI naming `SystemRoot::private_loadScripts` and `ScriptLoader::private_loadScriptFile`. `SystemRoot` has secondary vtable `0x4454c98` at offset `0x8`; `ScriptLoader` has vtable `0x445a488`. Names and vtables alone do not identify a callable reload method or provide object lifetime, context, or thread requirements. Steinberg's [MIDI Remote getting-started guide](https://steinbergmedia.github.io/midiremote_api_doc/getting-started/) documents the Script Console reload button; it does not establish a background API for invoking reload.

## Startup marker static evidence

The UTF-16 text `ApplicationStarted.txt` at executable RVA `0x482bca0` is held in a pointer at RVA `0x552ff08`. The pointer is loaded at RVAs `0x3ac5605`, `0x3ac5865`, `0x3ac5c9b`, `0x3ac5d57`, and `0x3ac5f66`. At functions `0x3ac5c70` and `0x3ac5d30`, the marker string enters a path-construction call; the same global object's virtual method at offset `0xe8` is called with that path, and if it returns nonzero its method at offset `0xe0` is called with the path. This pattern is consistent with a test followed by a path operation, but method semantics, caller identity, normal-exit behavior, and the relationship to the Safe Start dialog are not proven by this trace. `scripts/project-lifecycle-inspect.py` includes these exact references. Any controlled marker-move experiment and its live result must be recorded separately; the static finding itself performs no file operation.

## Reproduction and status

Run `python scripts/project-lifecycle-inspect.py` with `pefile` and `capstone` to print bounded disassembly of the fixed candidate methods and window procedure. This reads the executable from disk only and creates no file. The fixed offsets must be re-established after any application update. Supporting RTTI/vtable extraction uses `scripts/host-project-inspect.py` with narrowly scoped patterns; the RTTI association and the window procedure entry are independent static observations.

No native project lifecycle call, script reload, MIDI notification, or persistence operation was made by this investigation. A safe next step is to determine the notification callback's concrete object identity and callers, and separately recover a lifecycle interface with defined argument ownership, main-thread dispatch, asynchronous completion and verified disk outcome before implementing any operation.

`project-candidate-observation.md` records a later bounded current-process candidate and a separate static check showing that `PArrangement` constructs an `MRoot` at `+0x108`. The candidate's sampled root matched the global project root, but active selection, canonical path and lifecycle completion remain unproved.
