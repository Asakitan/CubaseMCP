# MIDI Remote activation dispatch: static evidence

Build: Cubase AI 16.0.5 Windows x64, PE timestamp `0x6adf121b`. This analysis uses only the executable on disk. RVAs are not a public or stable interface.

The prepared activation execute method at `0x2638280` is vtable slot `+0x08` of RTTI `SystemPreparedCommandActivateDevice`. It obtains a system root and calls `0x263b7f0` with the command object as the third argument. The creator `0x26383d0` is referenced at `SystemServiceCommands` vtable slot `+0x188`. It allocates a `0x58`-byte reference-counted allocation, installs the prepared-command vtable on the subobject at allocation `+0x10`, initializes its state and copies `[RDX+0x18]` to command `+0x38`. It then replaces the shared-reference pair at `[RCX+8]`/`[RCX+0x10]`, releasing its previous reference, and returns the new subobject pointer. This establishes creation and ownership operations, not the meaning of the copied identifier or the factory's full interface contract.

The factory is virtual, so its vtable reference does not identify an actual caller or prove scheduling. A bounded search for common x64 indirect-call encodings using displacement `0x188` in RVAs `0x2500000..0x2700000` returned several candidates with unrelated receiver provenance; none is established as a call on this service. The search omits other instruction encodings, code ranges and modules, so it is not evidence that no caller exists. The command's actual dispatch condition, executing thread, prepared arguments and public background entry remain unresolved. In particular the existing script construction and open MIDI ports do not prove that this factory or execute slot ran.

Reproduce the bounded factory and execute disassemblies with `python scripts/midi-detection-predicate.py --target prepare_command` and `--target prepared_execute`. The script checks the PE machine and build timestamp and does not open a process.
