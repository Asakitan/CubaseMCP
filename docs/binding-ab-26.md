# Binding A/B 26 — isolated controller preparation

The controller and offline fixtures are prepared only: no installation, launch, host operation or MIDI write by this controller was performed. The two entry files select default and Jump in separate intended processes. The default target is `0.625`; Jump target is `0.375`. Both use bank slot 0 volume, fixed UID `604DE95A858E93754BEA0BE43A9D6B2`, and DirectAccess tag `1025`. This identity/tag relationship is based on session 25's prior observation and must be revalidated in each new disposable fixture. Neither of the prior Piano 0.25 or Stereo Out 0.75 unknown submissions is replayed.

## MIDI and protocol

Dedicated exact port names are `CubaseAI Binding26 To Cubase` and `CubaseAI Binding26 From Cubase`, distinct from production. `protocol.js` uses 7-bit SysEx framing with header `[240,125,66,65,50,54,1]`, ASCII JSON fragments and FNV checksum. Requests have version `v:1`, unique 32 lowercase hex `id`, `op`, a safe-integer epoch-millisecond `deadline`, and, except `status`, the exact session returned by status. The deadline must be strictly later than the current clock at MIDI admission and idle dispatch; write and restore check it again after identity/value checks immediately before submission. An expired or invalid request consumes its ID and returns `not_started`; duplicates return `prior_outcome_unknown`. The deadline cannot cancel a submission already invoked. Each setter call marks the request submitted immediately before invocation; an exception after that boundary reports `execution:unknown` even when its error text is `DEADLINE_EXPIRED`. Output is a corresponding encoded JSON response. The only operations are `status`, `baseline`, `write`, `read`, and `restore`; no arbitrary host operations exist. The receive queue holds eight and tracks 256 one-time IDs for the controller lifetime. Malformed or unmatched-device frames are dropped; queue saturation and request-limit rejections report `not_started`, subject to the bounded response buffer. A missing response is not permission to resend an operation. Idle has a reentry guard and emits at most one response fragment each tick.

`baseline` validates active mapping, bank channel unique ID and runtime ID against the DirectAccess object, unique tag 1025, finite normalized value and unlocked state. It rejects an already-present target. `write` rechecks identity, tag, lock and exact baseline within 1e-6, consumes its one-shot admission before invoking the surface, and returns `unknown` regardless of synchronous echoes. `read` independently calls DirectAccess; only a target value within 1e-6 admits `restore`. `restore` rechecks identity, tag, lock and current target, consumes its single admission before the surface call, and reports `restore_unknown` until a later DirectAccess read matches baseline. A mismatch before submission is `not_started`; failures after submission remain unknown. Deactivation invalidates the session and baseline without resetting the one-shot write guard. Sixty-four latest time-stamped per-binding, surface and host events are bounded with a drop count; callback matching requires the active device and, where applicable, mapping.

## Interpretation and execution gate

Separate fresh process and copied fixture, exact host process lifetime, independent durable request admissions, collection of every MIDI fragment, and no replay across controller reloads are obligations of the external orchestrator, not enforced by the controller. Its in-memory guard does not survive reload or process restart. The controller does not verify the OS process, fixture file identity, foreground state, mapping activation stability, or durable persistence. The same channel identity and tag are used in two isolated copies, but target values, process and time differ; these are confounders alongside unspecified-versus-explicit Jump. A difference supports a hypothesis, not proof of default mode or cause. Surface, host and binding callbacks are observations, not independent completion evidence. DirectAccess baseline/readback also does not establish saved project persistence. A temporary-port smoke while the previous Cubase instance was running preceded a device-deactivation log and a status timeout; create experimental ports before launching the owned test process and close them only after it exits (`binding-test-ports-26.md`). Review source, fixture identity mapping and orchestration before any future execution.

Offline fixture command: `node --test tests/binding-ab-26.test.cjs`. Eight controller tests passed in the session 26 full suite. The fixture simulates propagation or surface-only echoes; it does not model actual Cubase behavior.




## Standalone client

`scripts/run-binding-ab26.cjs` is blocked as a real CLI: it exits with `LIVE_EXPERIMENT_NOT_ADMITTED` before loading or opening MIDI. Its exported `run` requires an injected fake driver and test admission directory; this injection interface is for offline tests, not a security boundary against a caller deliberately injecting a real driver. A future separate orchestrator must establish complete admission before enabling a live client, without connecting to production MCP. The offline implementation uses only the exact port names above and the isolated protocol. The caller supplies the arm and externally verified process-lifetime claim; the script does not itself verify PID, creation time, fixture, observer, desktop, or ownership. It generates a random run ID and unique request IDs and performs at most one `status`, `baseline`, `write`, `read`, and conditional `restore` in that order. Requests use a fixed 2500 ms deadline. Any timeout, disconnection, protocol rejection, identity mismatch, or unexpected response stops the sequence without replay. A single independent DirectAccess read must match the baseline object and target before restore. The final restore response is `restore_unknown`, not independently verified by this one-read client.

After status and baseline, immediately before write the offline client creates `binding26-<pid>-<creation-filetime>.json` in its injected test directory exclusively, writes the run ID, arm, session, baseline and target, and flushes the file with `fsync`. Its process-lifetime filename deliberately excludes arm so an existing admission blocks a second arm for the same claimed lifetime. It is a conservative consumed marker, including when submission later fails; preserve it and do not remove it to retry. The file flush is not a guarantee against every filesystem or power-loss failure, and independently verifying both process lifetimes and the distinct fixtures remains an external gate. Output includes the claim, operation responses, read events, and final outcome; timeout or disconnect after admission is `unknown`. Never treat missing output as a reason to resend.

Offline client fixture command: `node --test tests/binding-ab-client-26.test.cjs`. Eight client tests passed in the session 26 full suite. They use injected fake MIDI endpoints and a temporary admission directory, not real ports or Cubase.
