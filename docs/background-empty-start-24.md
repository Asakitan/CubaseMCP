## Review risks

The process-name check and process creation are not atomic with third-party launches; the named mutex serializes only participants using this empty launcher, not the older launcher or a user start. The current fixed desktop name and state require coordination with an existing holder; the running Cubase guard must reject the currently observed instance. Failure after process creation but before receipt persistence causes the holder to exit and its Job close can terminate its newly created child; this is not a no-side-effect failure. Receipt identities use separate process queries and can race fast exits; a missing receipt or timeout is an unknown launch outcome, never grounds for replay. The startup observations are samples rather than continuous foreground monitoring, and a restricted desktop Job does not establish application readiness or absence of all foreground effects. Executable-path trust, mutex scope/security, PID reuse, file path/reparse handling and cleanup remain operational constraints.

The background coordinator requires a caller-supplied lowercase 32-hex `-RunId`; holder receipt uses `artifacts/runtime/cubase-empty-launch-24-RUNID.json` with `HostPid`, `ProcessId`, `Desktop`, `mode: empty`, `Project: null`, process and holder creation FILETIMEs, sample time and Job flags. Receipt uses CreateNew and is never overwritten. The holder derives the same ID from paired log names.

`CubaseDesktop.StartEmpty` shares the existing suspended-process, desktop and restricted-Job core with `Start`; the latter now requires a nonempty project. `tests/empty-start-job.ps1`, `tests/desktop-job-boundary.ps1`, and `tests/background-empty-existing-guard.ps1` passed; their evidence is under `artifacts/empty-start-tests-f5ca949babab48578f6227c72b6319f1/`. The running-instance guard did not create another Cubase process. This is one diagnostic launch, not an MCP lifecycle operation.

Before the authorized restart, owned fixture files and the previous receipt were copied to `artifacts/runtime/before-empty-24-e6ef5f706a6f436896265a73a0ba82a3/`. The prior zero-byte `ApplicationStarted.txt` marker was moved into that backup while the prior owned process was stopped; preferences were not modified. A first canonical-receipt `File.Replace` call with a null backup path failed before replacement; a subsequent metadata-only replacement with an explicit backup path succeeded. The two earlier host-open submissions remain `unknown` and were not replayed.
