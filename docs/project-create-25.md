## New finding

The action handler beginning at `0x1d50ad0` compares the action-derived string first against ASCII `New` at `0x42ec288` (`0x1d51486`), then against `NewWithHub` at `0x42ee1a0` (`0x1d514d8`). On a `New` match, `r14b == 0` branches to the same `0x1ae0340` call at `0x1d5150d` as a `NewWithHub` match with `r14b == 0`; with `r14b != 0`, `New` instead calls `0x1ae0030` and returns the inverse of its byte result, while `NewWithHub` takes another branch. These are static control-flow observations, not proof of invocation, command availability, creation, or a no-dialog route. The follow-up below traces `r14b` to an action comparison and identifies a conditional Hub service call; the higher-level meanings remain open. The shared call makes assuming that plain `New` bypasses the Hub especially unjustified.

## Follow-up: action mode and Hub service

The handler initializes `r14d` to zero at `0x1d50af5`; the path reaching the comparison loads the address of ASCII `CanInterpret` at `0x419fae0`, calls `0x3a8cdc0` with `r15` and that literal at `0x1d5108d`–`0x1d51097`, and writes the returned `al` to `r14d` at `0x1d5109c`. Thus the New branch's discriminator is derived from this action-and-name comparison, not an independently proven UI or project state flag. The exact semantics of the comparison and all reachability conditions remain unresolved. For `New` with nonzero result, `0x1ae0030` tests whether a global manager lookup of `SmtgHubWindow` returns non-null; the handler returns the inverse of that Boolean. This is consistent with a query path, but its higher-level contract remains unproved.

For the zero-result path, `0x1ae0340` first checks the same `SmtgHubWindow` lookup and exits when it is non-null. It also requires a non-null global receiver and a non-null result from `0x1adfb70`. That helper queries a manager with ASCII `Hub Service` at `0x4271bd0` and traverses returned candidates when a cached value is absent. The caller allocates two wrapper objects containing or capturing the global receiver, calls the resulting service receiver's virtual slot `+0x18` with pointers to the wrapper subobjects, and releases the wrappers afterward. This is concrete evidence of a conditional Hub service invocation, not proof that a window actually opens, which concrete service implementation runs, or how long it retains either wrapper. The method receives no explicit directory, filename, or template arguments from the action handler on the traced call. Wrapper content, service callback targets, dispatch thread, selection and created-document ownership remain open. A hidden UI or project selection remains possible; do not treat this as a prompt-free create candidate.

The next static step is to identify the concrete service implementation and wrapper callback vtables at RVAs `0x4271b70`, `0x4271b88`, `0x4271be8`, and `0x4271c00` only after verifying their actual referenced addresses, then trace their method targets toward template selection and destination construction. No deeper parameterized creation entry has yet been established.
