# MIDI Remote host-port detection path

Date: 2026-11-10. This is a disk-only analysis of Cubase 16.0.5 Windows x64 (PE timestamp `0x6adf121b`); no running process, configuration or UI was touched. RVA and C++ layout observations are build-specific and not a supported host API. The exact operation that triggers a working instance remains unproven.

## Detection scheduling and predicate

RTTI for a `std::function` implementation explicitly names a lambda nested in `SystemHostEnvironment::ensureUpdateDeviceDetection`. Its vtable at `0x4456d40` has invocation slot `+0x10` at thunk `0x2619d50`, which adjusts `RCX` by eight and jumps to `0x26004f0`. Function `0x2623970` references that vtable at `0x2623d13` and constructs a callable containing state from its arguments. It calls `0x262df50`, gets the `SystemRoot` singleton, and branches at `0x26239d4` based on root `+0x130`; nonzero follows a path that can install the callable into an object from the environment's `+0x208` and pass it through helper `0x244d3b0` if a separate global object exists. The exact scheduler, timing, queue lifecycle and meaning of the pointer at root `+0x130` are not yet proven. Zero uses a different callback path; the comparison does not mean the script is disabled.

The complete `SystemRoot` constructor at `0x25e9b01` initializes `+0x130` to zero. The root's secondary vtable at offset `+8` dispatches to `0x2635650`; that method stores its incoming `RDX` at secondary `+0x128`, i.e. complete-root `+0x130`, and a subsequent conditional cleanup at `0x2635c3e–47` compares and clears the complete-root field. These are observations of a transient pointer-like field; its pointee type and ownership are unknown. A single zero snapshot cannot establish that no detector ever ran. Nine direct relative-call sites to `0x2623970` were found: `0x25db1bd`, `0x25fde48`, `0x2622562`, `0x2622972`, `0x26358e7`, `0x2635dd6`, `0x2636991`, `0x2637c59`, and `0x263be31`. The labels and triggering circumstances of all callers are not established.

Within the detection lambda, `0x2601723–0x2601757` checks a non-null candidate and equality of its instance-vector begin/end at `+0x1d0/+0x1d8`, then calls the `ScriptLoader` predicate described in `docs/midi-detection-predicate.md`. Only after that predicate returns nonzero does it load the candidate's detection-unit vector at `+0x88/+0x90` (`0x260175d–0x260177c`) and enter the unit loop. Thus a previously observed pair of open OS ports does not prove execution reached matching, and the predicate occurs in this detection callback as well as in the separate prepared-activation command path. The callback also exits early if its weak-reference/model setup fails; the exact preceding condition that applies to the current process has not been measured.

## Host-port model and candidate comparisons

The callback obtains a model through `0x30b3e40` and reads an object reference from model `+0x50`. The RTTI-identified `HostEnvironment` constructor `0x301b6b0` initializes vector-shaped fields at `+0x28/+0x30/+0x38` and `+0x40/+0x48/+0x50`, and its vtable is `0x45fa638`. The callback passes object `+0x28` into helper `0x25bb870` at `0x2600abc–0x2600ad2` and object `+0x40` into helper `0x25bb9f0` at `0x2600b48–0x2600b66`. The helper calls and vector traversal establish two distinct candidate collections, but the association of each particular live pointer with input versus output still requires a verified runtime type and cross-reference; do not label unknown collections based solely on order.

The model also contains `HostMidiInput` and `HostMidiOutput` RTTI, with vtables `0x45fa5a8` and `0x45fa608`, and respective constructors `0x301c7d0` and `0x301c9e0`. The input constructor initializes an MSVC string-shaped member at `+0x28`; additional string/identity fields and semantics must be validated before use. A comparison helper `0x25dbc10` traverses two input vectors and performs a length and byte comparison at `0x25dbe68–0x25dbebb`, as well as three conditional comparisons at `0x25dbe29–0x25dbe62`. This is a concrete string-comparison path, but the exact object types at that site and whether it is the name-only auto-detection filter versus saved-binding reconciliation have not been proved. No claim is made that exact matching occurred in a live process.
