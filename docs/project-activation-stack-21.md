## Candidate scan, not a call stack

The memory buffer was scanned as aligned 64-bit words. A word was retained if it fell inside the main image's PE exception-directory function range and the five preceding on-disk bytes began with `E8`; the relative immediate was decoded as a possible call target. There were 66 such words. This is an intentionally narrow filter: it omits indirect calls, other modules and leaf functions; the `E8` byte is not by itself proof of an instruction boundary. The image exception entries provide containing function ranges only, not an unwind from the actual thread context.

For illustration, the aligned word at stack-limit offset `0x86358` had candidate return RVA `0x36752ba`, contained in runtime-function range starting at `0x3675130`, and its preceding `E8` bytes resolve to RVA `0x3aab410`. The aligned word at offset `0x86408` had candidate return RVA `0x37b6490`, in a runtime function starting `0x37b6480`, with preceding `E8` bytes resolving to `0x3675130`. Their apparent adjacency in a possible call graph is **not** proof of instruction boundaries, live frames, ordering, causation, or any relationship to the activation prompt. Another candidate at offset `0x86bc8` resolves from return RVA `0x3935230` to target RVA `0x3936270`; a separate word at `0x86b98` has return RVA `0x393629f` within the function beginning at `0x3936270`. Such relationships are leads only.

The prior request remains `unknown`; no prompt decision, project activation, or open completion was observed here. A reliable current stack walk needs a trustworthy register context and matching unwind state; a running thread's TEB and raw stack alone do not supply either. Future read-only work can statically validate candidate instruction boundaries and their resource references while retaining the distinction between hypotheses and observed frames. Any stronger live context capture must separately satisfy the no-suspension/no-injection boundary and avoid assuming a passive mechanism exists.

## PSS context design and permission preflight

During the permission preflight, the caller's integrity level was Medium and the Administrators SID was deny-only. A non-elevated `OpenProcess` for `PROCESS_QUERY_INFORMATION | PROCESS_VM_READ` (`0x410`) and `OpenThread` for `THREAD_QUERY_INFORMATION` (`0x40`) both succeeded; the latter's creation FILETIME was `134387250823263010`. These handle-open observations alone were not a PSS capture or a complete specification of PSS's required privileges. No privilege was enabled during this preflight.

The proposed x64 diagnostic would revalidate the process FILETIME and thread ownership and creation time through retained handles, and revalidate the mapped image identity. It would request only `PSS_CAPTURE_THREADS | PSS_CAPTURE_THREAD_CONTEXT` (`0x180`), with x64 context flags sufficient for control and integer registers; it would not request a VA clone, handles or an address-space copy. The API captures contexts for **all** threads, not just the selected thread. Walk `PSS_WALK_THREADS` using a marker, select the matching process/thread IDs and creation time, validate `SizeOfContextRecord` and the record flags, and copy only the needed context while the marker is alive. Record capture status, selected thread's capture time, RIP/RSP and module-relative frames, errors and bounded metadata only. Free the marker, free the snapshot with `PssFreeSnapshot(GetCurrentProcess(), snapshot)`, and close handles on every path; record cleanup failures separately. `ContextRecord` is marker-lifetime storage, not target memory. [PSS_THREAD_ENTRY](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ns-processsnapshot-pss_thread_entry), [PssWalkSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psswalksnapshot), [PssCaptureSnapshot](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/nf-processsnapshot-psscapturesnapshot).

**Material limitation:** the requested flags do not capture stack page contents. A later bounded external stack read is not simultaneous with the captured register context; stack changes or thread exit can invalidate a walk, and neither matching unwind metadata nor a plausible trace proves temporal consistency. A `StackWalk64` implementation would pass a copy of the captured context, initialize PC/frame/stack, limit frame count and reads, use local image/PDB paths only with no symbol-server access, and report missing data and all per-frame confidence limits. The use of a local symbol path does not supply consistent stack memory. See [PSS capture flags](https://learn.microsoft.com/en-us/windows/win32/api/processsnapshot/ne-processsnapshot-pss_capture_flags) and [StackWalk64](https://learn.microsoft.com/en-us/windows/win32/api/dbghelp/nf-dbghelp-stackwalk64).

The cited Microsoft API descriptions do not establish that thread-context capture has zero transient thread-freezing or scheduling impact. No explicit `SuspendThread` call is made, but this is not proof of zero internal freezing. Even an observed stack sequence would not independently identify the dialog, its decision conditions, or completion of the earlier request.

## Context-only diagnostic

`native/ActivationSnapshot21.cpp` and `scripts/Build-ActivationSnapshot21.ps1` were reviewed and built. The executable is fixed to the above PID, process creation FILETIME, TID and thread creation FILETIME. Before capture it checks retained process/thread handles, liveness, executable path, loaded main-module base, in-memory x64 PE machine and timestamp, then enumerates the private `CubaseAI_MCP` desktop for an owned window and a visible owned `Cubase AI` title. This title is a baseline only, not semantic proof of a particular prompt or project. Identity is rechecked after selecting the thread entry. Captured output is limited to the selected thread's capture time and RIP/RSP/RBP plus errors; PSS internally captures all thread contexts, but the diagnostic does not print them or dump memory. Marker/snapshot/handle cleanup status is checked on the normal capture path.

The implementation intentionally omits `StackWalk64` and symbol lookup. No synchronous stack-page snapshot is requested, and a robust bounded read callback, verified module/unwind information and an explicit classification of live-read races are prerequisites for any future walk. A lone captured register context does not identify the prompt's call chain. MSVC `/Zs` and `/W4 /WX` build passed, followed by one successful isolated capture; PSS's internal scheduling or freezing impact remains unspecified in the cited API documentation.
