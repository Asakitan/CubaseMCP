# First-project open 26: proposed one-shot admission contract

Status: an offline source draft and two distinct byte-compared fixture copies exist; no session 26 Cubase launch, build, injection or host-open has been performed. Session 24's PID 72128 module and fixture admission are consumed; sessions 19 and 20 remain unknown. None is eligible for replay. This proposal needs implementation and review before a future independent experiment.

## Scope and fixed authority

The intended observation is one first-project open submission against a newly owned no-CPR launch and a new local disposable copy, not project creation or persistence. Retain the session 24 private desktop, restricted Job, fresh zero-project preflight, independent observer, fixed Cubase build and fixed diagnostic entry. No foreground operation, desktop switch, input synthesis or automatic retry is admitted. Do not turn the implementation into a generic process injector, arbitrary path opener, shell command runner, or configurable native-call facility.

## Proposed per-run binding

1. A single-purpose orchestrator generates an unpredictable run ID internally and starts the established owned empty-mode launcher with no project argument. It must derive the child PID and creation FILETIME from a retained process handle, and derive the holder PID and FILETIME from its retained handle. Reject an existing instance, stale receipt, project argument, dead handle, wrong executable or mismatch between handle and receipt. PID alone, an independently supplied receipt path, and timestamps derived from wall-clock alone are insufficient authority.
2. Create a dedicated local run directory beneath the fixed workspace artifacts root with CreateNew semantics. Resolve the root and every component by handles, reject reparse points and remote volumes, and record volume serial plus file ID; do not rely on a lexical prefix. Copy only the already specified local source to a fixed generated fixture basename using exclusive create, retain identity and compare its bytes directly. Require a distinct source and destination file ID; later recheck identity, final path and bytes immediately before submission. Reject existing destination, links, replacement, unexpected source, changed content or path. Do not accept a caller-supplied path. A filesystem identity check cannot guarantee Cubase will later open the same object by pathname: document this residual race and stop if exclusive ownership/ACL and path stability cannot be established.
3. Bind immutable manifest values: run ID, target and holder PID + creation FILETIME, launch mode and empty project argument, private desktop, Job identity and restrictions, fixture volume/file ID/final path/size, approved executable and diagnostic-module build profile, observer identity and deadline. Verify version, PE architecture/timestamp/size and the existing in-memory vtable/profile checks; independently verify the loaded image corresponds to the approved image. Version or timestamp alone is insufficient. Fixed function offsets must be tied to the verified exact build.
4. Seal this manifest to the newly launched run using an inherited/duplicated handle or equivalent single-run capability with restricted access, not an untrusted JSON file or public PID/path parameter. The future loader, preflight, observer and in-process worker independently check the same bound identities. Audit the same holder-owned Job via a retained/duplicated Job handle, verify target membership and expected UI and kill-on-close restrictions; revalidate holder lifetime. A receipt's booleans alone do not prove actual Job membership or permissions.
5. Start a separate observer tied to the run and its own PID + FILETIME, acquire its ready record only after its first sample, and retain its process handle. Require a live observer and sufficient monotonic deadline through the irreversible call, with final independent results afterward. Polling and foreground-window desktop scope leave transient events potentially unobserved; never claim continuous foreground exclusion. A ready file alone is not proof of a running observer.
6. Immediately before admission, perform the existing bounded read-only fresh preflight: same process lifetime and exact image/profile, stable null global root, empty project list and informer tree, expected listener. Repeat inside the target immediately before the call along with Job, background input desktop, observer and event-thread checks. Checks are non-atomic; record sample time and residual race. An empty preflight is evidence of state at sampling, not a lock preventing state changes.
7. Atomically consume one durable per-run admission before any module load or attempted host call, using exclusive creation and flush. The durable key must bind the target lifetime as well as run ID; a new run ID must not bypass an existing consumed admission for the same process lifetime. A crash, timeout, absent result, failed flush, partial record, changed identity or uncertain submission consumes that admission and requires evidence-based investigation, never automatic retry. Fail closed on ambiguous state. Do not delete or reset consumed records.
8. The dedicated module entry receives no caller-selected executable, function, offset, path or payload. Bind the fixture using a single-run capability/manifest with strict schema, integrity and ownership; have both loader and module verify the immutable run binding and reject substituted identities. Pin the module and retain the in-process one-shot guard. Duplicate the session 24 host-call shape only after independent source review; preserve the existing object lifetime constraint. If a trustworthy binding across loader and injected module cannot be established without introducing arbitrary PID/path capability, stop at design rather than relax the contract.

## Evidence and outcomes

Write exclusive, durable per-run start/admission/result records, with exact process and fixture identities, build fingerprint, observer and preflight references, stage transitions and timestamps. Record submission result separately from independent project-root/path observations and observer outcome. A successful return is submission only. Missing, timed-out or incomplete observation remains unknown; a displayed title or matching lexical path does not prove file identity, active selection, save destination, clean state or durable persistence. Restrict fixture and evidence access to the local test account; avoid claiming tamper resistance against an administrator or same-user process without a proven isolation mechanism.

## Gaps before approval

- The session 24 loader, observer, preflight, Job audit and native worker hard-code PID 72128, holder PID 55324, their FILETIMEs and fixture path; replacing these with freely supplied parameters would defeat their fixed-target guards. A reviewed, capability-bound redesign is required at every layer.
- The existing observer contract records PID, creation time and deadline but does not itself authenticate a fresh run or prove ongoing sampling. Define a non-forgeable cross-process binding and liveness semantics before implementation.
- A trusted run-scoped capability, retained handles, file-identity checks, collision-resistant consumed-target ledger and crash semantics are not present in this document and must be implemented and reviewed, not assumed.
- The host opens by path; retained file handles and pre-call identity checks do not eliminate the pathname race. Establish enforceable directory ownership and sharing behavior, or leave the experiment blocked.
- No assertion here establishes that the historic fixture is safe for a new test, nor that a newly launched host is ready. Verify source identity and actual empty startup in the future run.

## Generator review: blocking authority gap

The observed empty-launch receipt is ordinary JSON containing `RunId`, `mode`, `Project`, process and holder identities and Job flags. Its filename and contents do not authenticate the launcher, prove that it created the process, prove that the holder owns the particular Job, or bind either process handle to a future generator. Checking PID + FILETIME, executable version, path and receipt values improves identification but does not establish ownership. A user-supplied run ID selecting such a receipt would indirectly select an arbitrary matching process; emitting a callable fixed-target source from it would therefore violate the no-arbitrary-target contract.

The two fixed fixture names `Binding26Default.cpr` and `Binding26Jump.cpr` constrain the requested file names, but neither is itself a mode or run ID inside the existing receipt. The current receipt records `mode: empty` and `Project: null`; it does not bind a binding experiment mode or fixture to the launch. Require a trusted launch transaction that creates both processes and passes retained handles plus the run ID and fixed mode through a restricted capability before implementing a generator. File-based evidence and user-input JSON are audit material, not launch authority. The actual Job must be queried through a handle and target membership checked, not inferred from flags. Existing preflight and native code also hard-code the old identity, observer contract, result paths and fixture; blind text substitution is not a reviewed adaptation.

At that review point no generator or executable static source had been emitted. This was a contract gap, not a failed live experiment; no launch, compilation, injection or submission was performed.

## Narrowed review contract

The dispatcher specified a narrower non-adversarial same-user threat model and a fixed plan at `artifacts/ipc/binding26-plan-RUNID.json`, bound to `midi-startup-empty-arm-RUNID.json` and the empty launch receipt. Its `default` and `jump` modes map exclusively to `Binding26Default.cpr` and `Binding26Jump.cpr`, respectively; the fixed source is `artifacts/live-smoke/MCP Device Test 20261110.cpr` (93085 bytes). Under that assumption, parent-process and live Job checks can support bounded operational provenance, but remain separate from cryptographic authentication. The plan-preparation and validation scaffolds below implement some of these checks; their combined positive path against a new target is not verified and they do not admit execution.

The session 24 native template additionally embeds the observer-contract filename and the entry export as well as identities and fixture path. A generator must verify exact replacement counts for all of these, fail on unmatched old literals, write with CreateNew, and preserve the one-shot and observer checks. A matching receipt or plan does not by itself establish the other checks. The later offline draft below is deliberately not executable.

## Offline template draft implementation

`/scripts/FirstOpen26Template.psm1` now contains a pure fixed-template substitution function and a CreateNew draft writer under the fixed `artifacts/first-open-26-drafts` directory. Exact historical-marker counts are checked; the two fixture names are selected only by the two enumerated modes. All drafts begin with `#error NOT_ADMITTED_FIRST_OPEN_26`, and the writer returns `not_admitted`. They are neither buildable nor authorized to load. The writer does not establish launch provenance, arm/plan/receipt agreement, fixture identity, Job membership, desktop status, observer readiness or one-shot execution admission. The earlier statement that no generator exists refers to the admitted generator; this draft is offline scaffolding only. Path-reparse checks are not atomic against a concurrent change.

Focused offline test: `tests/first-open-26-template.ps1` passed under Windows PowerShell and PowerShell 7. It tests both modes, case normalization, rejection of an old target and invalid mode, creation of an unbuildable draft, and a rejected CreateNew collision that preserves the first draft. The two fixture copies were subsequently created and byte-compared as documented in `binding-fixtures-26.md`; no target build, injection, restart or host request was performed.

## Plan validation scaffold

`/scripts/FirstOpen26Plan.psm1` adds a fixed-run, fixed-mode validator for the specified plan, arm and receipt paths. It checks their declared agreement, retained target/holder/trace process objects and creation times, target parent, unique Cubase process, executable path/version/base and empty command line, fixed fixture byte equality, plan/arm ordering and the live holder Job. Success is always `not_admitted`: it does not independently audit private desktop ownership, enforce the host PE fingerprint, run first-project preflight, validate an observer, or atomically bind validation to draft creation. Plan last-write time is not proof of original CreateNew time; paths and process snapshots have race windows. Caller-supplied values remain insufficient authority for loading the separate draft writer's output. No positive invocation against a new run was performed.

Focused offline rejection test: `tests/first-open-26-plan.ps1` passed under Windows PowerShell and PowerShell 7 for malformed mode/run ID, missing fixed records and UTC precision. Positive combined validation on a new target and cross-step handle retention remain unverified.

## Live Job-audit implementation

`native/FirstOpen26JobAudit.cs` adapts the session 24 bounded system-handle snapshot to already-open target and holder process handles. It checks handle PIDs and creation times before and after the snapshot, duplicates candidate holder-owned Job handles with `JOB_OBJECT_QUERY`, checks target membership, and requires exactly one match with UI flags 64 and limit flags 8192. Duplicated handles, marker and allocated buffers are released in `finally`; caller-owned handles are retained by the caller. `FirstOpen26Plan.psm1` invokes the audit after its other checks and still returns `not_admitted`, because desktop ownership, exact image fingerprint, observer, fresh preflight and atomic binding remain outstanding. The audit may reject when process handle permissions or the bounded snapshot are insufficient; it does not retry.

Focused tests `tests/first-open-26-job.ps1` and `tests/first-open-26-plan.ps1` passed on both PowerShell engines. The Job unit test checks repeated invalid-handle rejection, not every resource-cleanup branch. Separately, a read-only audit of the existing owned PID 72128 and holder PID 55324 found one matching Job with flags 64 and 8192 (`artifacts/ipc/first-open26-job-final-6b643f82724fa787ae94f9473ed2c9f3.json`). This is not a new-run plan validation. No target injection, restart or host request was performed in this slice.

## Process identity sampling

`native/FirstOpen26ProcessIdentity.cs` replaces the two CIM process queries in the plan validator. It samples the Toolhelp process parent and command line twice around held-handle PID, creation-time and liveness checks; mismatch or failure stops. The command-line query uses `NtQueryInformationProcess` class 60, an implementation-dependent interface rather than a documented compatibility guarantee. Its bounded 64 KiB local buffer, returned length and `UNICODE_STRING` pointer/length are checked before copying; failure has no retry or alternative channel. Snapshot and lifetime checks are sequential, not atomic, and a parent PID is not a retained parent handle. The holder handle and its lifetime are separately verified by the plan and Job checks.

`tests/first-open-26-process-identity.ps1` passed on both PowerShell engines for current-process reading, wrong-creation rejection and an independently spawned hidden child's parent and command line. A separate read-only call on PID 72128 observed its holder PID 55324 and the quoted no-project-argument command line in 20 ms (`artifacts/ipc/first-open26-process-identity-c38141fb6c097a2eb9a9e4730dabb4c5.json`); that single timing is not a performance guarantee. No injection, restart or host request was performed.
