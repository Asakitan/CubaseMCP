# MIDI Remote host-port producer

Static disk-only analysis of Cubase AI 16.0.5 Windows x64 (PE timestamp `0x6adf121b`). Existing PID 3720 observations are recorded in `docs/midi-host-environment.md`; no new process read or process/configuration/UI operation was performed here.

The previously identified input and output insertion instructions belong respectively to `0x313d390` and `0x313d770`. A scan for direct relative calls in executable sections found one call to each: `0x2635fba` and `0x26365bf`. Both belong to `0x2635d80`, which is slot `+0x00` of the RTTI-identified `SystemHostEnvironment` vtable at `0x4454a40`. This is evidence of a producer path, not evidence that there are no indirect calls or calls from other modules.

At entry, `0x2635d80` first invokes detection scheduling `0x2623970` with two zero reference pairs. It then examines its incoming `RDX` object: a virtual call at slot `+0x00` requests an interface into a local output, another virtual call at `+0x10` must return nonzero, and the resulting interface's slot `+0x38` must accept the literal `PPort` with flag 1. A wrapper initialized by `0x29b0430` must also return nonzero. It subsequently branches on the wrapper's `0x29b05f0` result: one branch reaches the input producer, and the other reaches the output producer after their respective environment lookups. The first branch calls the port interface slot `+0x100`, performs string conversion, and passes the resulting string plus an environment weak reference to the input producer; the other branch performs analogous preparation for the output producer. After input creation the returned object's `+0x18` is stored into a separately obtained object at `+0x38`. Equivalent instructions follow output creation. Later tracing identified the wrapper's `I|`/`O|` direction test in `docs/midi-host-port-adapter.md`; the requested interface's full semantics, event source, thread, port visibility, and separate object's type remain unresolved.

Thus the zero host-port vectors seen in the prior snapshot are consistent with this path not being entered, any of its gates failing, later removal, or other state transitions; static call references and a point-in-time snapshot do not distinguish those possibilities. The vtable and `PPort` literal are not a documented externally callable host API, and no event-injection or bypass procedure is established.

The next read-only evidence should first establish the lifetime and concrete type of the input interface and its owner/event registration using static RTTI/vtable references, then inspect only a proven bounded owner/listener field in a freshly validated private PID. An arbitrary guessed interface pointer or virtual call would not distinguish missing event delivery from an intentional rejection.

Reproduce bounded disassembly of `0x2635d80` with the existing script engine, for example by loading `scripts/midi-device-state-inspect.py` via `runpy` and assigning this RVA in its in-memory `FUNCTIONS` dictionary. No script file or process needs modification.
