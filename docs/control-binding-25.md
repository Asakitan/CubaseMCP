# Control binding investigation 25

## Scope and current evidence

This note distinguishes an offline model comparison from separate observations of the current host. Session 24 recorded the 3.8 mapping activation and a Piano selected-track volume submission whose target 0.25 was not observed within two seconds. A subsequent control and DirectAccess read still reported 0.7890625. This unconfirmed request must not be replayed. The separately observed Stereo Out DirectAccess volume and edit-lock round trips concern a different object and mechanism; they do not establish selected-track binding propagation. See `docs/first-project-open-24.md` and its referenced artifacts for the current-process evidence; the earlier legacy core-chain success belongs to an earlier process and revision.

## Static finding and falsifiable distinction

`remote/controller.js` creates a custom surface value and binds it to the selected host value with `makeValueBinding`. A control write invokes the surface's `setProcessValue`; the controller marks that call as `submitted`, suppresses its synchronous surface echo, and accepts a matching host-value callback as observation. The test fixture's `makeValueBinding` only stores the host value; its `setProcessValue` emits a surface callback but does not propagate a host change. Thus the default fixture does **not** model host binding propagation. Another existing test explicitly injects a synchronous host callback. Neither model establishes Cubase's actual behavior.

The paired tests in `tests/remote.test.cjs` model surface echo only and an injected host callback without connecting to Cubase. Surface echo alone retains the previous observation while both models report `submitted`; the host callback model records its new value. They distinguish submission from modeled feedback but do not reproduce real host propagation.

An independent session 25 test targeted the distinct Stereo Out bank channel 0, not the earlier Piano selected-track request. The bank slot identity and DirectAccess parameter matched before one `cubase_control_set` submission to `0.75`. Both DirectAccess and bank feedback still showed `0.7890865802764893` after submission (`artifacts/ipc/bank-volume25-result-23cccf22-7a9a-487e-9487-3c5c9b5feba9.json`) and in a later read-only snapshot (`artifacts/ipc/bank-volume25-later-read-a2632972-ba27-4037-acc5-345b8f44b95f.json`); no restore was submitted because the target was not observed, and the one-shot admission is consumed. A separate desktop observer recorded 173 samples with `Default` input desktop and no sampled target foreground (`artifacts/ipc/first-project-open24-observer-72128-0a4630a2a228a9d628e1a6353c65f024.json`). Polling does not prove continuous foreground history. These two affected channels make a single Piano-only explanation less likely, but do not identify the cause. The earlier successful DirectAccess volume test used a different API path and is not a retry of either control submission.

The official [MIDI Remote API reference](https://steinbergmedia.github.io/midiremote_api_doc/codedoc_api_reference/) declares `setProcessValue` on surface values and `setValueTakeOverModeJump`, `setValueTakeOverModePickup`, and `setValueTakeOverModeScaled` on value bindings. The current source does not explicitly choose a takeover mode; whether the active host default or callback context accounts for the observed behavior is a hypothesis, not a demonstrated cause. A future experiment must use a distinct guarded operation with independent host readback and preserve both unconfirmed requests without replay.

## Installed declaration and candidate discrimination

The installed Cubase 16 `.api/v1/midiremote_api_v1.d.ts` declares `MR_ValueBinding.mOnValueChange(activeDevice, activeMapping, currentValue, valueDiff)` and the three takeover setters. `MR_HostBinding` / `MR_ValueBinding` expose no documented active-binding or current-takeover getter in that declaration. The accompanying `.api/v1/midiremote_api_v1.js` methods return `this` and are API stubs, not evidence of host runtime implementation, semantics, or a default mode. Page `mOnActivate` establishes mapping activation, not an individual binding's activity. `mOnValueChange` is a promising per-binding event observation, not a query or proof of completion; the installed Novation Launch Control XL 3 `host_bindings.js` assigns it on a custom-variable value binding. The installed Steinberg simple-device example binds a hardware knob to selected-track volume without an explicit mode; Avatar EMP-16 explicitly uses Jump on certain quick controls, while Arturia KeyLab Essential explicitly uses Scaled on fader-volume bindings. These examples establish usage only, not the host default or how custom variable input is routed.

A future independent minimal-controller experiment would require a separate isolated process and disposable fixture, with no modification to the production controller. Compare separate custom variables and distinct targets under otherwise matching identity, context and value trajectories: one default binding, one explicitly Jump; log timestamped page activation, device/mapping identities, binding `mOnValueChange`, surface and host callbacks, and independent DirectAccess reads, including a no-input baseline. Predefine distinct operations and outcome/timeout rules; do not repeat either existing unknown request. A difference between the two arms would support a mode-dependent effect, not by itself establish the default mode. If both fail, that leaves custom-surface routing or context and other mechanisms open; if both succeed, investigate production context and scale. Merely installing or activating the separate controller changes host state, so this remains a design, not an executed read-only check.
