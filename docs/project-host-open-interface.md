# Host project-open interface: component call evidence

Target: installed Cubase AI 16.0.5 x64 executable, timestamp `0x6adf121b`, and its installed `Components/vstconnect.dll`, timestamp `0x647e2a79`. Static evidence is build-specific, not a published SDK contract. The static investigation invoked no host method; the separately approved fixed in-process path-service lookup is recorded below.

## Receiver and input conversion

Cubase `UPluginContext`'s RTTI hierarchy includes `IHostApplication2` at complete-object offset `+0x08`. The context query at `0x3752105` compares raw IID bytes `c1 3c b1 43 75 1b 32 44 a0 9c d9 52 7c 1d d0 ac` and returns that secondary subobject. Its vtable `0x4737230` slot `+0x18` targets `0x3751d40`. This associates a host interface with the method; it does not show that an arbitrary external plugin or the MCP process receives the required context.

Static initializer `0x1580030` writes that class's vtables into consecutive image locations beginning at RVA `0x55233f0`, including the `IHostApplication2` vtable at `+0x08` and an `IHostClasses` vtable at `+0x68`. The latter's slot 0 is a thunk subtracting `0x68` and jumping to the same context query; slot `+0x18` reaches `0x3ab0b90`, which forwards an IID to a service registry and stores the returned pointer. This has the same broad query/service-call shape used by the shipped component, but it does not prove that component's context field points to this particular subobject or that a live lookup succeeds. The earlier DAWproject trace documents the same service-locator branch in `dawproject-host-context.md`.

`scripts/Read-PluginContextStatic.ps1` validates the isolated launch PID, private-desktop window ownership, process start, executable version, PE timestamp and image base, then reads the fixed static object without invoking a method. In PID 39068 at `2026-11-09T18:09:26Z`, two reads of the first six vtables and of the `+0x68` vtable matched the static profile (`artifacts/ipc/plugin-context-static-39068-661ca8ff13a24ad5b063ec3d1302e4e4.json`). The observed complete object was `0x1455233f0`, with host-open subobject `0x1455233f8` and host-classes subobject `0x145523458` for that process and instant only. This unlocked snapshot does not establish service readiness, current project identity, lifetime, synchronization, a valid caller or a callable project operation; addresses must not be reused for another process.

The host method treats its incoming `RDX` and optional `R8` as **interface objects**, not raw filenames. It converts each through `0x3b0d3f0`, which queries an IID and calls virtual methods on the input; one conversion branch recognizes `FNPath`, while another constructs an `FNPath` and copies data obtained from the input object's virtual methods. The exact input interface contract, ownership and supported path encodings remain unverified.

The second raw IID also matches a query branch of `FPath` at `0x3b0f2a0`, which returns its `+0x10` subobject. RTTI identifies both `IPath` and `IPath2` bases at that offset, and the secondary vtable `0x4832cb0` slot `+0x20` targets `0x3b183d0`, which forwards to the complete object's virtual slot `+0x178`. This associates the requested IID and slot with the path object family; it does not independently distinguish the two inherited interface names or specify a portable public ABI.

Static initializer `0x15bd9f0` passes the same raw IID, factory callback `0x3b0ed80` and record at RVA `0x59a03d0` to registration constructor `0x3b8f020`. The constructor copies the IID to record `+0x18` and the callback to `+0x28`, and contains conditional registry-insertion calls. The callback allocates an `FNPath`, installs its primary and `+0x10` secondary vtables, and returns the `+0x10` subobject. RTTI identifies both path-interface bases there; secondary slot `+0x20` reaches `0x3b0f4b0`, which calls the `FPath` setter. The static path alone does not prove a live factory call or a portable ABI.

At `2026-11-09T18:15:37Z`, the bounded PID 39068 diagnostic separately double-read the fixed registration record and the class-factory CID hash table (`artifacts/ipc/plugin-context-static-39068-369280693a8f403d810bd41e03dff202.json`). It verified the factory and table vtables, hash-function pointer, bucket bounds, total count, linked-node lengths and tail pointers, then reread the headers, all 254 nodes and the records in the expected bucket. The table had 20 buckets; the IID's statically derived hash was bucket 6, which held one matching IID and the observed record as the first match. The record's callback matched `0x3b0ed80`. This snapshot alone was not a live lookup or factory invocation; duplicates outside the hash bucket, concurrent changes between rereads, object lifetime, thread safety and subsequent operation outcomes remain outside its proof. Context, record and registry reads are separate unlocked snapshots, not an atomic combined snapshot.

A later, separately approved one-shot in-process diagnostic used the observed `IHostClasses` subobject to request that fixed IID in isolated PID 39068. The call returned zero and an object with the expected `FNPath` secondary vtable; the fixed release call returned, without a path setter, project method or UI action (`artifacts/native-probe/path-result-39068.json`). This establishes that this lookup and object-release call worked in that process at that time. It does not show the `vstconnect.dll` field points to this context, establish a general thread contract, or validate an open/create/save/edit operation; see `native-probe.md`.

A separate fixed diagnostic image subsequently constructed another temporary `FNPath`, called its setter once with a synthetic Unicode absolute path and mode `0`, and directly compared the bounded directory and filename fields before releasing it. Both fields matched in PID 39068, and the fixture CPR path was absent before and after (`artifacts/native-path-roundtrip/roundtrip-result-39068.json`). This validates one setter/input representation and object-field split in that process, not the public getter, canonical disk identity, general lifetime or host-open behavior. The static setter, filesystem root-check slots and fixed PE profile are reproducible with `scripts/project-path-roundtrip-inspect.py`; see `native-probe.md` for the diagnostic bounds.

After conversion, a state-dependent branch calls the application vtable slot `+0x178` with the first and optional second converted objects. Another branch constructs a `ServiceAction` named `OpenFile`, supplies `Path` and, when present, `ProjectDir`, then passes it to `0x3a8d370`. The latter branch returns zero after submission without a demonstrated completion callback. Neither branch establishes a prompt-free open, project creation, active-project identity, main-thread execution, or durable save; the second path is not evidence of a public command-line `ProjectDir` option.

## Independent shipped-component caller

In `vstconnect.dll`, RTTI identifies `YYVst3HostAccess`'s secondary vtable at `0xb6be80`, complete-object offset `+0x10`; its slot `+0x98` targets `0x1d1180`. This method queries its context field at receiver `+0x68` for the same host IID. It separately requests raw IID `a1 8e f3 0a f2 40 14 4b 96 5b f9 7c a4 ff 94 d1` through that context's slot `+0x18`, calls each returned object's slot `+0x20` with data derived from an incoming argument, and passes one or two of those objects to the acquired host interface's slot `+0x18`. It releases the retained interfaces on the shown paths. The names, initialization contract and lifetime of those objects, the meaning of the context's service IID, and the component's initiating event or thread remain unresolved.

A process-identity-checked module snapshot found `vstconnect.dll` loaded in isolated PID 39068 (`artifacts/ipc/vstconnect-module-39068.json`). Static constructor `0x1ce250` writes the object to a tree rooted at module global `0x100b9f0`; it later initializes the complete object's `+0x78` context field to zero. A bounded, unpinned read of that one tree header at `2026-11-09T18:02:48Z` observed a validated sentinel and count zero (`artifacts/ipc/vstconnect-hostaccess-header-39068.json`). It is a point-in-time observation of this one registry, not proof that all host contexts or instances are absent. A loaded module does not prove a usable context, an executed method, or a project open. A plugin-factory context or VST3 `VstHostContext` must not be assumed to be the same object as `UPluginContext`.
