# MIDI informer project notification dispatch

Static-only follow-up for Cubase AI 16.0.5 x64, PE timestamp `0x6adf121b`. The coordinator's independently collected private PID 3720 evidence establishes that the `MProject` listener chain includes informer `+0x20`, while informer `+0x88/+0x90` has zero entries at that snapshot. It does not establish that no prior project notification occurred.

The callback `0x25b17f0` is slot `+0x18` of the informer `IProjectNotification` subobject; it inserts a non-null `RDX` pointer as the key in the informer `+0x88` ordered tree. `MProject` registration uses the interface and listener container described in `docs/midi-project-gate.md` and `docs/dawproject-host-context.md`.

A subsequent coordinator trace identified one dispatch with receiver provenance. In `0x279e640`, `RCX` is used as `MProject` and the non-null incoming `RDX` is saved in `RSI`; after state checks the function stores `RSI` at `MProject+0xf8`. At `0x279e88a` it obtains the list at `MProject+0xc8`, constructs an iterator through `0x279e1e0`, and subsequently iterates that same list. At `0x279e994–0x279e99b` it passes `RSI+0x98` to each non-null listener's slot `+0x18`. The statically traced existing-project open routine `0x1d42430` directly calls `0x279e640` at `0x1d43957`, after earlier state-dependent work. This is one concrete sender and is distinct from unrelated indirect calls at the same slot.

For the separately observed PID 3720, `MProject+0xf8` pointed to an object whose exact vtables identify `MRoot` at offsets `0` and `+0x98`; its observed `+0x98` address was `0x79143038` (`artifacts/ipc/dawproject-host-context-main-3720.json`). Thus the dispatch would pass that subobject when its incoming object is this same observed `MRoot`; the static and snapshot facts do not establish that this invocation occurred after the informer registered, that the object is the active document, or that a later removal did not occur. There is no evidenced normal background re-synchronization procedure or justified direct notification invocation.

The registration path's `MProject` slot `+0x30` reaches `0x16022f0`, which allocates a linked-list node, copies the listener pointer into it, links it and increments the list count; this method itself does not call the newly added listener. Separately, `0x279e640` compares the incoming root with the existing `MProject+0xf8` at `0x279e676`; equality immediately returns a true byte at `0x279e67b`, before the later listener dispatch. These facts make registration/selection ordering a specific hypothesis worth investigating and show that simply invoking the same-root branch would not reproduce the later dispatch. They do not establish the actual startup ordering, prove that notifications were missed, or justify invoking either function.

The next discriminating evidence is the ordering and conditions of project-root selection versus informer registration, including the normal sender's full thread and lifecycle contract. A controlled startup-order comparison may be useful only when it can preserve the owned project copy and respect the background-only constraint. Prior listener presence plus an empty notification tree remains a point-in-time state, not proof of event non-delivery.
