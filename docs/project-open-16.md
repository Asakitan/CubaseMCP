## Scope

Read-only static and bounded process observations for Cubase AI 16.0.5 x64, PE timestamp `0x6adf121b`, preferred image base `0x140000000`. No predicate, host method, queue consumer or project operation was called; no foreground action, keyboard, mouse or dialog input was requested. Continuous foreground observation was not performed. RVAs are build-specific, and snapshots are unlocked observations rather than lifecycle guarantees.

## Thread-sensitive branch

In `0x3751d40`, the receiver from global RVA `0x5973dd0` is adjusted by `+0x10`, then called at slot `+0x88`. In isolated PID 39068, repeated reads observed that subobject's vtable `0x4713f68`; its RTTI is `Steinberg::UController`, offset `+0x10`, with the `IPlatform2` base. Its slot resolves to `0x3674c90`, which calls `0x37b4a20`, then tail-dispatches its result at slot `+0xb0`.

`0x37b4a20` calls `0x37b4a40` and dispatches the returned object's slot `+0x48`. `0x37b4a40` first calls `0x3920bb0`, which returns global `0x597d000` plus `8` when non-null; otherwise it follows a different static-initialization path. In the observed process that global was non-null, its secondary vtable `0x4797908` had RTTI `Steinberg::UI::Platform::Win32Factory`, and slot `+0x48` was the leaf `0x18f7d00`, returning its receiver plus `0x40`. Consequently, on these exact observed pointers and slots, the next receiver would be global pointee plus `0x48`.

That object's observed vtable `0x4799968` is `Steinberg::UI::Platform::Win32EventHandler`, secondary offset `+0x10`, slot `+0xb0 = 0x3935710`. This function calls imported `GetCurrentThreadId`, compares it to the 32-bit value at receiver `+0x178`, and uses `sete al`: equal gives 1 and the host-open direct branch; unequal gives 0 and the posted branch. The observed value was `25212`. It is therefore a *calling-thread-dependent* predicate, not a global boolean. A future worker's actual TID must be compared at the time of its call; a sampled value is not a stable authorization or thread-affinity contract.

## Queue limits and future test boundaries

The caller passes the application pointer as `FPostedMessage` receiver. The append helper invokes `0x3a87fd0`; that leaf only tail-calls the message's slot `+8` when queue word `+0x14 == 2`, and otherwise returns. It has no explicit operating-system wake call in that leaf. Consumer `0x3a8c220` has multiple host call sites, including `0x3675d2d` in a condition-dependent branch of `0x3675cf0`; no current evidence proves when that branch executes or on which thread. Consumer dispatch remains conditional, and the application `OpenFile` handler discards the called open method's result (`project-dispatch-15.md`). No correlated completion/error callback or exhaustive prompt and foreground audit is established.

In the posted branch, the host calls the converted path's slot `+0xc0` before assigning the returned object to an action property with argument `1`, and releases its local converted references before returning. For the observed `FNPath` vtable, that slot allocates a new object and calls a copy constructor. The property setter maps argument `1` to flag `0x20`; the examined property helper calls the supplied object's slot `+8` only when flag `0x10` is present. The posted-message constructor directly stores the action and application receiver, while the traced destructor releases the action and does not show a receiver release; the consumer later queries the receiver. These are fixed-build static paths, not a complete ownership contract: deep-copy behavior, property destruction, failure cleanup and application lifetime remain unproved. `scripts/project-open-lifetime-16-inspect.py` checks the relevant RTTI and slots and prints these ranges from runtime-function beginnings.

An eventual single test requires one isolated project copy and recorded before-state; continuous foreground and private-desktop window observation; actual thread and queue-delivery evidence; a correlated, independently verified project root/path change; and prompt/error monitoring. Unknown outcome must stay unknown and the operation must not be replayed. At present the unverified wake/consumer thread, potential dialogs and foreground actions, input lifetime and completion correlation prevent a justified real-open call under the stated constraints.

For sampled state bytes `0/0`, the static application slot's branch at `0x1d53be9` skips its own additional `OpenFile` submission and continues into further path-dependent processing. The slot can conditionally call the larger routine at `0x1d42430`, which rechecks the state bytes; the selected branch and all prompt paths are not established. The executable's normal imports include `SetForegroundWindow`, and the separately studied second-instance route contains a call; the normal imports do not list `SwitchDesktop`. Those import observations do not rule out dynamic resolution or calls from other modules, and do not establish reachability from this open route. A private desktop and periodic observation alone are not proof that no foreground or desktop switch occurred.
