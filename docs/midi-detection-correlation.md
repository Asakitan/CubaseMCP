# MIDI detection correlation: scanner and registry paths

Date: 2026-11-10. Static findings apply only to the installed Windows x64 Cubase 16.0.5 build with PE timestamp `0x6adf121b`. Existing snapshots are read-only, separately timed observations; no process, port, configuration, or UI changes were made in this slice.

## Two distinct paths and a five-byte condition

Steinberg's [device detection documentation](https://steinbergmedia.github.io/midiremote_api_doc/api-details/detection-unit/) describes port-name detection and SysEx identity expectations as distinct criteria; its name-based example does not specify an identity response. This is a public API contract, not proof of a particular internal branch or successful detection in the observed session.

At `0x25afff0`, a non-null scanner global at executable RVA `0x58f8d00` is required. For each supplied `0x88`-byte record, `0x25b0040–0x25b004c` skips the record if the difference between its `+0x68` and `+0x60` detail pointers is less than five bytes. The next calls, `0x22dc9e0` and `0x22dca80`, each must resolve a non-null interface. Two further slot `+0xd8` calls at `0x25b0354` and `0x25b0392` must return true. Only after those checks does `0x25b03c6–0x25b03d3` pass informer `+0x68` and the first interface's resulting wrapper to `0x25ad570`; `0x25b03d8–0x25b0501` clears the returned node's byte vector at `+0x50` and copies the record's detail bytes into it. The second wrapper is obtained and checked, but its complete role and the meaning of the copied bytes remain unresolved. The five-byte test is a gate on this scanner-processing path, not established proof that all name-only detection requires a five-byte identity response.

The scanner callback `0x25af030` reaches that function. Separately, registry refresh `0x25b0a40` collects qualified registry entries and replaces the informer's port tree at `+0x58/+0x60` at `0x25b153e–0x25b1590`, before passing scanner `+0x358` to `0x25afff0` at `0x25b15fe` onward. The observer registration path `0x25aecd0` traverses the `+0x58` tree, while adapter callback `0x2635d80` branches by the constructed input/output port key and can populate host-environment collections. See `docs/midi-host-port-adapter.md` and `docs/midi-informer-tree.md` for the traced conditions. These are separate tree offsets and paths; their complete interdependence and event order remain unproven.

The informer's fourth tree is at `+0x88`, count at `+0x90`. The Idle handler `0x25af940` requires a nonzero `+0x90` among other checks before calling registry refresh. A subsequent static trace identified one `IProjectNotification` insertion path that uses the supplied pointer as the tree key; its event semantics and live execution remain unresolved. See `docs/midi-project-gate.md`. The scanner detail copy above writes the separate `+0x68` tree. A zero snapshot of `+0x90` therefore establishes only that this particular nonzero test would fail at that instant, not the history of detection, a disabled driver, or a general requirement for SysEx.

## Observations and verification boundaries

`artifacts/ipc/midi-scanner-state-3720.json` recorded two scanner entries with the expected MCP port names and zero-length detail ranges. If those exact records were passed unchanged through `0x25afff0`, both would take its skip branch. `artifacts/ipc/midi-port-registry-names-3720.json` separately records four expected-name socket objects and empty informer trees; the distinct earlier `artifacts/ipc/midi-host-environment-main-3720.json` snapshot records empty host-environment vectors. These snapshots do not prove that the scanner callback or Idle handler ran, that the registry's `midi`/`system` virtual filters accepted those sockets, or why the tree counts were zero. No successful detection or root cause is asserted.

For a reproducible static check, run `python scripts/midi-detection-correlation.py --target scanner_filter`; the other fixed targets expose the callback, Idle gate, refresh, observer registration, adapter, and candidate match. The script verifies PE machine and timestamp and disassembles one bounded runtime-function range from disk. For further live observation, use only fresh independently validated launch identity, process start time, executable, vtables and double-read bounds as in the existing read-only snapshots. Compare registry names, `+0x58/+0x60`, `+0x68/+0x70`, `+0x88/+0x90`, scanner record detail headers and host-environment counts at each observation; record timestamps and reject unstable reads. Such samples can correlate state but do not reveal event history. Investigate the project-notification registration and insertion prerequisites described in `docs/midi-project-gate.md`; no internal function invocation or process mutation is established by this analysis.

The session 14 scanner registration and rebuild follow-up is in `midi-activation-14.md`. It identifies a standard inquiry registration and a static enumeration receiver but does not establish that name-only detection requires an inquiry response.
