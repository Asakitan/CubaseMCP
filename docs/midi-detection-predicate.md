## Static chain

The candidate instance-creation caller `0x263b7f0` calls `0x2672f00` at `0x263b966`. The latter is a direct jump to `0x2673740`, which returns the object at executable RVA `0x590b030`. Its initialization writes vtable RVA `0x445a488`; MSVC RTTI identifies that vtable as `ScriptLoader@ScriptLoading@System@MidiRemote@Lego@Steinberg`. At `0x263b96b–0x263b97c` the caller invokes slot `+0x28` on that object, passing the previously obtained driver pointer, and proceeds toward instance creation only when the returned `AL` equals 1. Earlier guards and port binding are described separately in `docs/midi-device-state.md`.

The slot `+0x28` implementation is `0x26739a0`. It initializes a temporary string and invokes the loader's slot `+0x08`, `0x2672d90`, with the driver and string output. That method obtains a 64-bit lookup key from driver `+0x18`, searches the loader's first ordered tree rooted at object `+0x08`, and copies the corresponding string from matched node `+0x28`. An absent node or empty string causes the predicate to return zero. If it obtains a nonempty string, the predicate calls `0x26735d0` to obtain a second global ordered string tree at RVA `0x590b018`; a matching string makes the predicate return zero, and a missing string makes it return one. The exact lifetime, synchronization and ownership contracts are not recovered.

The first tree's observed binary-search node layout is left/parent/right pointers at `+0/+8/+0x10`, sentinel byte `+0x19`, numeric key `+0x20`, and MSVC string-shaped value at `+0x28` with size `+0x38` and capacity `+0x40`. The second tree's string-shaped key begins at node `+0x20`, with size `+0x30` and capacity `+0x38`. These are static observations, not stable serialization formats. All external traversal requires strict bounds and stable-header checks.

The second-tree getter has thread-safe singleton initialization. It allocates an empty sentinel then calls `0x2674ac0`, which reads data through a path-like global object at RVA `0x590ad60`, parses text and inserts strings. A separate method `0x2679a10` calls the first lookup, adds or removes that returned string according to a boolean argument, and calls `0x26762a0` to write a representation through that same path-like object. This supports describing the second tree as a persisted rejection set for this predicate. Its schema and relation to the UI's disabled-script setting are not established.

More precisely, `0x2674b02` calls `0x2662190` which returns the global base `0x590aca0`, and `0x2674b07–0x2674b13` passes base `+0xc0`, i.e. `0x590ad60`, to `0x3b0ecd0`. The latter's helper `0x15cf9e0` returns its argument unchanged before the path object is constructed and then passed into the stream-like path at `0x2670fe0`. This establishes the field-to-reader data flow, not the exact filesystem semantics of every virtual call.

## Prepared activation command

The sole direct relative-call hit to `0x263b7f0` found in executable sections is `0x263829d`, within function `0x2638280`. The latter is slot `+0x08` in the vtable at `0x44557d8` whose MSVC RTTI names `SystemPreparedCommandActivateDevice`. It obtains a root through `0x262dfd0`, supplies its own object as the third argument, calls `0x263b7f0`, and writes either zero or the resulting object's `+0x18` value into command offset `+0x40`. Function `0x26383d0` allocates and initializes that command object. A reference at vtable slot address `0x4454c08` associates this factory method with the `SystemServiceCommands` vtable starting at `0x4454a80` (offset `+0x188`). These observations support a prepared-device-activation command path; they do not establish when or why a real detection attempt schedules or executes it, or that it ran in PID 45628. No virtual call was made in this investigation.

The matched node's contents were not independently reread in that evidence, so concurrent change is not ruled out.

The coordinator separately observed second-tree head/count `0/0` and static initialization guard at RVA `0x590b028` as four zero bytes (`artifacts/ipc/midi-detection-guard-45628.json`). Zero is not a valid constructed sentinel pointer. It is not evidence of an empty initialized rejection set, an enabled script, or a disabled script. Because a successful first lookup in the predicate reaches the getter, these snapshots are consistent with the predicate not having reached that getter while the current lookup state existed; startup ordering, earlier/later state changes, concurrent access and singleton implementation details prevent treating this as proof of non-execution.

My local `Get-Process -Id 45628` returned no result, whereas the coordinator reports the private process remains alive; the live values above are coordinator-provided observations, not independently repeated from this agent.
