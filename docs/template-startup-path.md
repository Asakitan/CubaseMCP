# Template startup and ProjectDir evidence

This investigation read existing source, setup artifacts, stored verification and installed executable bytes only. It did not operate a desktop, project, configuration, process or memory. Historical evidence is not a new live test.

## Historical comparison

Session 02 records copying the installed AI `Piano Page Layout.cpr` template to `artifacts/live-smoke/MCP Smoke.cpr`, starting that copy on an isolated desktop, and explicitly handling safe-start and project-directory prompts during a separately approved one-time initialization. `artifacts/live-smoke/verification.json`, dated `2026-11-09T14:25:19.263Z`, records a successful 16-tool MIDI handshake, Piano parameter discovery, volume feedback, write and restoration on Cubase 16.0.5. Its saved session and result do not identify the preceding root-selection callback, exact timing of initialization actions, or the current 3.5 bridge.

The ignored setup helper verifies the private window's PID, then its `ConfirmFolder` branch sends `WM_COMMAND` with command ID 1 to the observed folder dialog; it is an interactive initialization mechanism, not a parameterized project API and was not invoked here. The checked-in launcher currently uses the AI template only when no explicit project path is supplied, copying it if `MCP Smoke.cpr` does not already exist. When given `-ProjectPath`, it instead uses that existing file and its parent directory. Both variants pass the parent as the Windows process **working directory**, and `CubaseDesktop.Start` builds a command line containing only quoted executable and quoted project path. A process working directory is not itself proof of a Cubase project-directory argument. Source today does not prove the exact code revision at the earlier successful startup.

The later `MCP Recovered 20261110.cpr` was copied from the autosave and `MCP Device Test 20261110.cpr` is an experimental modification of a saved MIDI Remote instance block; see `midi-autodetection.md` and `midi-instance-experiment.md`. Their open/construction records and subsequent timeouts are not the earlier successful handshake. The later `artifacts/live-smoke/launch.json` now refers to recovered PID 64024, not the session-02 verification process; the old receipt in `artifacts/runtime/test-project-before-restart-20261110/launch.json` records PID 11368 without a project path. These differing file and receipt states prevent deriving a single controlled causal difference. Prompt handling, initial root ordering, stored project content, controller revisions, host state and process lifetime are confounders.

## Native action argument provenance

In the installed executable the existing `openProject` handler at `0x2900aa0` fetches its `path` argument and calls application virtual slot `+0x178` with that object in `RDX` and `R8=0`; see `project-lifecycle-contract.md`. The statically identified derived target `0x1d53bb0` preserves `RDX` in `RSI` and `R8` in `R15`. Under a separate global-state condition it constructs an `OpenFile` action and, if non-null, retains/adds `RSI` under `Path` and `R15` under `ProjectDir`. Thus this particular observed `openProject` call supplies no `ProjectDir` object; the conditional action supports an internal field, not evidence of a CLI option or a public way to supply it. The alternate path continues after the action submission, and argument object type, receiver, thread, selection and no-dialog behavior remain unresolved.

The official [Steinberg MIDI Remote getting-started guide](https://steinbergmedia.github.io/midiremote_api_doc/getting-started/) assumes a project has already been created; it does not establish a project creation or directory parameter API. No reviewed official source establishes a Cubase command-line ProjectDir option. `scripts/template-startup-path-inspect.py` checks the exact PE profile and literals and prints the relevant static calls. Passing a second argument, synthesizing an action object or calling this internal target is not warranted by these observations. A future comparison needs matching controller and process conditions, documented normal project selection and a direct correlation of root/activation ordering; successful initial verification alone does not isolate which historical condition caused activation.

The independently traced shipped-component path in `project-host-open-interface.md` can supply a second path-family object to a host interface. That finding does not change the `R8=0` observation for the action handler above and does not establish a supported command-line option or completed project operation.
