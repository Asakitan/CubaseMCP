# MIDI Remote automatic detection investigation

Date: 2026-11-10. Investigation was read-only: no script installation, preference edits, process restart, MIDI message injection or UI input. Project bytes were decompressed in memory only.

## Documented contract

Steinberg's [Device Detection documentation](https://steinbergmedia.github.io/midiremote_api_doc/api-details/detection-unit/) describes `detectPortPair` with port-name expectations and separately documents optional SysEx identity expectations. Its [Simple Device example](https://steinbergmedia.github.io/midiremote_api_doc/examples/simpledevice/) uses one pair with exact input/output names and no identity predicate. Therefore an identity exchange is not a documented universal prerequisite for a name-only pair. The example does not prove that every version or particular virtual-port combination activates automatically. A Steinberg forum discussion reports that one detection unit represents the complete set of ports for a device; the project uses only one pair in one unit, so the discussed multi-pair configuration issue is not directly applicable ([discussion](https://forums.steinberg.net/t/multiple-ports-not-recognized/846093/1)).

The installed entry constructs one driver, one input and one output, with `expectInputNameEquals('CubaseAI MCP To Cubase')` and `expectOutputNameEquals('CubaseAI MCP From Cubase')`. The project does not register `expectSysexIdentityResponse`. Windows MIDI enumeration via `@julusian/midi` showed exactly one input and one output with each configured name; the output list additionally had Microsoft GS Wavetable Synth. The persisted `Port Setup.xml` has both directions for the two names and does not itself prove what names the active MIDI Remote detector sees or that ports are enabled. Before the controlled hotplug, virtualMIDI client evidence listed PID 17596 for both ports; the replacement endpoints no longer list it after a delivered device notification (`artifacts/ipc/midi-clients-after-hotplug-17596.json`). Open ports do not establish a MIDI Remote device instance or mapping.

The main-thread trace reported controller construction but no device or mapping activation for PID 17596; a later connection also timed out. PID 45628 subsequently had an empty target-driver instance vector, and prior PID 3720 constructed revision 3.3 but timed out at status before any write (`artifacts/live-smoke/verification-coverage-3.3-3720.json`). PID 46868 constructed revision 3.4 but likewise timed out at status before writes (`artifacts/live-smoke/verification-coverage-3.4-46868.json`). Successor PID 39068 constructed 3.5, and a no-write status request timed out with outcome `unknown` (`artifacts/live-smoke/verification-coverage-3.5-39068.json`). Earlier successful live checks on a prior controller are recorded in `artifacts/live-smoke/verification.json`; they do not establish automatic activation on the current process or script.

The only current MIDI Remote `User Settings` file inspected is `CubaseAI_MCP_E0F0CC8CB80661B1193E987E61F07F58_globalmappings.json`. It contains the driver, named ports and user/factory mapping relationships, not an observed `DeviceInstance` or an explicit disabled flag. `UserPreferences.xml`'s inspected `MidiRemote` group contains runtime sign-in/update warning settings; this limited observation does not rule out hidden runtime disablement, other storage, port ownership conflicts or application-internal state. Steinberg documents that scripts may be disabled and that disconnected surfaces can be removed, but that UI documentation does not establish their current state or a headless management API ([controller settings](https://www.steinberg.help/r/cubase-artist/15.0/en/cubase_nuendo/topics/midi_remote/midi_remote_controller_settings_pane_r.html)).

## Saved project instance evidence

The `MidiRemoteSavedDeviceInstancesInProject_3` section was located in each of the following files and its following zlib stream was decompressed, verified to end and parsed as JSON. In all three, the decoded list contains exactly one driver `test` / `test`, created by `cdettner`, with one input and one output bound to `Mobile Keys 25` and a specific SysEx identity. None of the decoded entries is the `CubaseAI` / `MCP` driver. This is a saved project snapshot, not a live enumeration of all global or transient instances. The unrelated saved device uses different port names; its mere presence does not prove it blocks detection.

## Unresolved and next discrimination

There is no demonstrated background-only repair or authenticated runtime API here. Possible causes include a disabled script/instance, unresolved internal port pairing, device-instance persistence or activation timing; each remains a hypothesis. Name-only predicates and the existing port openings make a mandatory SysEx identity requirement an unsupported explanation. A bounded next diagnostic should observe the live MIDI Remote model's driver enabled state, detection result, candidate input/output names and instance lifecycle through an established read-only host interface, if one can be independently recovered. Compare exact runtime names and port UID/usage before changing anything. Do not rewrite preference files or project instance data based only on these static structures, and do not claim connectivity until an actual active-session handshake succeeds.
