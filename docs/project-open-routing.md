# Project open routing: bounded evidence

This slice used on-disk analysis already documented in `docs/project-lifecycle-contract.md`, a read-only inspection of Windows file-association registration on 2026-11-10, and official Steinberg documentation. It did not launch an instance, send a window message, operate UI, modify configuration or invoke a lifecycle method.

The local machine's `HKLM\Software\Classes\.cpr` default is `Cubase.Project`; `HKCR\Cubase.Project\shell\open\command` has the default `"C:\Program Files\Steinberg\Cubase 16\Cubase 16.exe" "%1"`. Enumerating the local `Cubase.Project` subtree showed `DefaultIcon`, `shell`, `shell\open`, and `shell\open\command`, with no DDE subkey. This establishes the registered shell command for a CPR path; it does not establish whether the process created by the shell continues, forwards the file to an existing process, activates an existing window, opens a separate project, or exits. The advertised installer command also exists and is separate from the default value. Registry state is machine-specific and can change.

The executable's `openProject` action handler `0x2900aa0` accepts an action object, extracts a `path` value, validates an `FPath`-type object, and calls application vtable slot `+0x178`. Static `PCubaseApplication` and `PSequencerApplication` vtables point to `0x1d53bb0`, which may conditionally construct an `OpenFile` action or follow other state-dependent branches, including a call to `0x1d42430`. This is a real native action route, but no observed command-line forwarding chain, external action dispatch ABI, main-thread synchronization, path-object ownership, prompt-free behavior, completion signal, or successful headless open is established. A shell argument is not an `FPath` object, and the action's existence does not prove the shell registration uses it.

Steinberg's [Cubase 15 opening-project documentation](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/project_handling/project_handling_opening_project_files_t.html) describes Hub and File > Open, says several projects may be open and an additional project may present an activation choice, and notes external projects can automatically connect audio buses. Its [activation documentation](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/project_handling/project_handling_projects_activating_t.html) says only one project is active at a time. These are version-15 public product descriptions, not proof of a particular Cubase AI 16 background invocation. [General preferences](https://www.steinberg.help/r/cubase-pro/15.0/en/cubase_nuendo/topics/preferences/preferences_general_r.html) describes opening the last saved project at startup; a preference of that name is not proof of current local settings or a no-project startup.

No validated standard native route currently demonstrates initialization of MIDI Remote with no project, followed by opening and activating the intended CPR without foreground interaction. Before proposing such an experiment, recover the secondary-process forwarding receiver and thread contract, or a documented lifecycle dispatcher with owned `FPath`, completion and dialog behavior. A controlled future test must isolate the project copy and verify which process receives the request, the active project, MIDI state before and after, and any prompt; do not infer these from the registered command.

An independent static follow-up found an installed component querying a host interface and passing one or two path-like objects to its open method, which can supply the internal `ProjectDir` field. The component and host call chain, execution branches and unresolved context/thread/completion limits are in `project-host-open-interface.md`; this does not establish a callable MCP operation or a CLI switch. A separate candidate second-instance forwarder contains a state-dependent foreground call and was not exercised; see `project-instance-routing.md`.
